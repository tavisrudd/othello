# C1018 — exact distance hunt for the bivariate-bicycle code [[756,16,d]]

**Lane**: `gem-mining`
**Date**: 2026-08-31
**Status**: complete

## Objective

Narrow or close the exact minimum distance of the bivariate-bicycle (BB) quantum
CSS code with parameters [[756,16,d]]. The repository's prior state certified
`d >= 24` by exhaustive connected-support search to radius 22; the published
source for this code reports only the heuristic upper bound `d <= 34`. This task
is a purely computational narrowing of a published record: no structural claim is
made or implied.

## 2. What an exhausted radius certifies

From the Ergodis README, `css_distance_native` "independently replays the
incumbent and exhaustively closes every smaller connected-support class", and
"Direct optimization uses parity-aware iterative deepening and anchor-level
Young-Brothers-Wait."

Concretely, a completed run with `--maximum-weight R` that reports
`result.distance: null`, `nontrivial_supports: 0`, and
`searched_maximum_weight: R` certifies: **no logical operator of the searched
type has support weight `<= R`**, hence `d >= R + 1`.

The extra `+1` that takes this to `d >= R + 2` is a parity fact about this
instance, not a generic rule. In `css_distance.rs` the compiler calls
`binary_all_ones_functional` over the physical check matrix and stores
`kernel_weights_even: kernel_parity_functional.is_some()`. That predicate holds
exactly when the all-ones vector lies in the row space of the physical checks;
when it does, every kernel vector `v` satisfies `<1, v> = 0`, so every kernel
support — and therefore every logical operator — has **even** weight. For this
input the predicate holds (the solver's parity-aware deepening is active and
skips odd radii), so an exhausted even radius `R` gives `d >= R + 2`.

### 3.5 Upper side: independent BP-OSD hunt

To attack the upper bound with a stronger decoder, a second, independent
implementation was written: `notes/2026-08-31-c1018-756-helper.py`. It stacks
the physical checks over the logical observations, `H = [P; L]` (394 x 756), and
for a random nonzero logical class `c` in GF(2)^16 decodes the syndrome
`(0, c)` with belief propagation plus ordered-statistics decoding (the `ldpc`
package, version 2.4.1). Any `e` with `H e = (0, c)` satisfies `P e = 0` and
`L e = c != 0`, so it is a genuine logical operator by construction; the script
re-verifies this over GF(2) rather than trusting the decoder, so a reported
weight is an exact upper bound regardless of whether BP converged.

| run | OSD method | order | error rate | trials | wall (s) | best weight |
|:----|:-----------|------:|-----------:|-------:|---------:|------------:|
| probe 1 | `osd_cs` | 5  | 0.01  | 8     | 0.3   | 84 |
| probe 2 | `osd_cs` | 15 | 0.01  | 3,000 | 284.5 | 56 |
| probe 3 | `osd_e`  | 10 | 0.002 | 3,262 | 260.5 | **44** |
| probe 4 | `osd_e`  | 10 | 0.002 | 2,620 | 260.0 | 74 (randomized channel priors) |
| probe 5 | `osd_e`  | 15 | 0.002 | 209   | 420.8 | 96 |
| refine 1 | `osd_e` | 10 | 0.002 | 6,018 | 250.0 | 44 (local search around the probe-3 witness, no gain) |

Replay of the best configuration:

```sh
uv run --with ldpc --with numpy python3 \
  /home/tavis/src/othello/notes/2026-08-31-c1018-756-helper.py \
  --input ~/.cache/ergodis/bb756/hx-gz.json \
  --trials 100000 --osd-order 10 --osd-method osd_e \
  --error-rate 0.002 --max-iter 300 --seed 1018003 \
  --time-budget 260 --out bposd-probe3.json
```

The best verified witness has weight 44. **This does not improve the record:
the published heuristic upper bound for this code is 34.** The comparison across
probes is itself the useful finding — breadth over logical classes beats OSD
depth here. Exhaustive-combination OSD at order 10 (1,024 combinations per
trial) over ~3,300 classes reached 44, whereas order 15 (32,768 combinations)
over only 209 classes reached just 96, and biasing the channel priors either
randomly or toward the incumbent's own support made things worse, not better.
The variance that matters lives across logical classes, not inside one class's
combination sweep, so any further attempt on the upper side should spend its
budget on classes.

### 3.6 Upper side: exhaustive sector scans

A cheaper exact question was also settled. Restricting the support to one half of
the coordinates collapses the search: the kernel of the physical checks confined
to coordinates `[0, 378)` has dimension 24, and confined to `[378, 756)` it has
dimension 8. Both are small enough to enumerate completely, so the minimum weight
of a logical operator living inside either half is an **exact** number, obtained
by enumerating all `2^24` and all `2^8` combinations of the respective sector
kernel bases with a doubling table and rejecting the ones the logical
observations do not detect.

```sh
uv run --with ldpc --with numpy python3 \
  /home/tavis/src/othello/notes/2026-08-31-c1018-756-helper.py \
  --input ~/.cache/ergodis/bb756/hx-gz.json --trials 0 \
  --sector-scan 0:378 --out sector-left.json     # 1.83 s
```

| window       | kernel dimension | combinations | exact minimum logical weight |
|:-------------|-----------------:|-------------:|-----------------------------:|
| `[0, 378)`   | 24               | 16,777,216   | 52                           |
| `[378, 756)` | 8                | 256          | 188                          |

Every returned witness is re-verified over GF(2) inside the script (physical
checks satisfied, logical observations nonzero), so these are genuine logical
operators and genuine upper bounds. Neither improves on 34, which settles a
question worth settling: **the minimum-weight logical operator of this code is
not supported inside either bicycle sector.** Any successor attack on the upper
bound must work across both halves.

### 3.7 Upper side: exact scans over translation-invariant subspaces

The same exhaustive trick applies to symmetry rather than support. The code's
metadata claims a `Z_21 x Z_18` translation action with two coordinate orbits.
The helper first *verifies* that claim against the data rather than assuming it:
it builds the permutation for each generator under the standard bicycle layout
(two sectors of 378 coordinates, each indexed `i * 18 + j`) and checks that
permuting the columns of the physical check matrix leaves its GF(2) row space
unchanged. Both generators pass, so the action is real for this instance.

For a translation `g`, the `g`-invariant logical operators form the kernel of the
physical checks stacked with `I + P_g`. For a high-order `g` that subspace is
small enough to enumerate completely, which gives the **exact** minimum weight of
a `g`-invariant logical operator.

```sh
uv run --with ldpc --with numpy python3 \
  /home/tavis/src/othello/notes/2026-08-31-c1018-756-helper.py \
  --input ~/.cache/ergodis/bb756/hx-gz.json --trials 0 \
  --symmetry-scan --symmetry-max-dimension 20 --time-budget 420 \
  --out symm-probe1.json
```

Of the 354 nontrivial translations of order 8 or more, 96 have an invariant
subspace of dimension at most 20 and 102 have dimension at most 26. Enumerating
all of them takes 37.3 s and 49.0 s respectively, and both passes return the same
lightest invariant logical operator, of weight 84. Since 84 exceeds the upper
bound 34, **no minimum-weight logical operator of this code is invariant under
any of those 102 translations.** Combined with section 3.6, the minimiser is
neither sector-supported nor appreciably symmetric, which rules out the two
cheapest structured routes to the upper bound and explains why a generic decoder
is left doing the work.

### 3.8 Upper side: the order-two invariant subspace

The symmetry scan of section 3.7 only enumerates subspaces small enough to
exhaust, which biases it toward large subgroups and therefore heavy operators.
A divisibility argument says where to look instead. A translation fixes a
coordinate `(i, j)` only when both of its shifts are zero, so every nontrivial
translation subgroup `H` acts freely and every orbit has exactly `|H|` elements.
The support of an `H`-invariant vector is a union of orbits, so its weight is
divisible by `|H|`. Subgroup
orders divide 378 = 2 x 27 x 7, and the admissible distances are 28, 30, 32, 34,
so the compatible orders are:

| candidate `d` | subgroup orders that could fix a weight-`d` operator |
|--------------:|:-----------------------------------------------------|
| 28            | 1, 2, 7, 14                                          |
| 30            | 1, 2, 3, 6                                           |
| 32            | 1, 2                                                 |
| 34            | 1, 2                                                 |

Order two is compatible with every candidate, and `Z_21 x Z_18` has exactly one
element of order two, namely `(0, 9)`. Its invariant subspace has dimension 197 —
far too large to enumerate, but small enough that randomised information-set
decoding inside it is easy, because a weight-34 vector need only avoid a
197-column information set rather than a 386-column one.

```sh
uv run --with ldpc --with numpy python3 \
  /home/tavis/src/othello/notes/2026-08-31-c1018-756-helper.py \
  --input ~/.cache/ergodis/bb756/hx-gz.json --trials 0 \
  --symmetry-scan --symmetry-only 0:9 --symmetry-isd-trials 1000000 \
  --symmetry-max-dimension 26 --seed 77001 --time-budget 5400 \
  --out sym2/o2-1.json
```

Sixty trials, in 32.5 s, produced a logical operator of weight **36** — against
44 for the best BP-OSD run, 52 for the best sector scan and 84 for the best
enumerable symmetric scan. That single structural restriction is worth more than
every generic method tried here combined, and it is the finding to carry forward:
**search the order-two invariant subspace first.**

Eight independent workers then ran the same search for 4,800 s each, on seeds
77001 through 77008, completing between 9,418 and 10,059 information-set trials
apiece for a total of 77,693. **Every one of them returned 36 and none found
anything lighter.** That is strong evidence, though not a proof, that 36 is the
exact minimum weight inside this subspace: with a 197-column information set
drawn from 756 coordinates, a weight-34 member would be caught by the singles
step with probability about `4.2e-4` per trial and by the pairs step with about
`2.4e-3`, so roughly 218 hits were expected across 77,693 trials had one existed.
The practical consequence is that **the published weight-34 operator, if it
exists, is not invariant under the order-two translation** — so the remaining
upper-bound work cannot lean on symmetry and has to attack the full kernel.

Exact rank computations pin down which invariant subspaces can contain a logical
operator at all. For a translation `g`, comparing the dimension of the
`g`-invariant part of the kernel with the dimension of its intersection with the
logical observations' kernel gives the number of invariant logical classes
exactly, with no search involved:

| generator  | order | invariant dimension | trivial part | invariant logical classes | information-set trials | lightest found |
|:-----------|------:|--------------------:|-------------:|--------------------------:|-----------------------:|---------------:|
| `(0, 9)`   | 2     | 197                 | 189          | 8                         | 77,693                 | 36             |
| `(7, 0)`   | 3     | 126                 | 126          | **0**                     | 24,133                 | none exists    |
| `(7, 6)`   | 3     | 126                 | 126          | **0**                     | 69,403                 | none exists    |
| `(0, 6)`   | 3     | 128                 | 124          | 4                         | 66,996                 | 54             |
| `(7, 12)`  | 3     | 132                 | 120          | 12                        | 62,563                 | 36             |
| `(0, 3)`   | 6     | 65                  | —            | —                         | 89,599                 | 84             |
| `(3, 0)`   | 7     | 56                  | 52           | 4                         | 126,303                | 70             |
| `(3, 9)`   | 14    | 29                  | —            | —                         | 454,895                | 84             |

The two zero rows are exact negatives obtained from rank computations alone, with
no search involved: for `(7, 0)` and for `(7, 6)` the entire invariant part of the
kernel lies inside the kernel of the logical observations, so **no logical
operator of this code is invariant under either of those two order-three
translations.** Half of the order-three subgroups are eliminated outright.

Every weight in the last column is divisible by its subgroup's order, as the
free-action argument requires, which is an internal consistency check on the
whole apparatus.

The order-three rows were the sharpest available test of the upper bound, because
divisibility by 3 combined with the even-weight parity of section 2 forces an
order-three invariant logical operator to have weight divisible by 6 — so below
36, the only value it could take is 30, and a weight-30 witness together with the
certified `d >= 28` would have cut the answer to 28 or 30. Roughly 130,000
information-set trials across the two subgroups that admit logical operators
produced 54 and 36, and nothing at 30. The test came back negative, so the
interval stands as certified in section 4.

The weight-36 witness was re-verified by a third, independent code path using
Python big-integer bitmasks rather than the helper's own numpy arithmetic: it
violates none of the 378 physical checks and triggers 11 of the 16 logical
observations, so it is a genuine logical operator. Its weight is even, as
section 2 requires.

## 4. Certified interval

Combining the radius-26 exhaustion with the published heuristic upper bound:

> **`28 <= d <= 34` for the bivariate-bicycle code [[756,16,d]],**
> and since every logical operator of this instance has even weight,
> **`d` is one of 28, 30, 32, 34.**

The repository's prior state was `24 <= d <= 34`, that is `d` in
{24, 26, 28, 30, 32, 34}. The exhaustion moves the lower end by 4 and cuts the
candidate set from six values to four. The lower bound is certified by exhaustive
finite enumeration; the upper bound is the published heuristic figure and is
**not** certified here. The lightest logical operator this task produced and
verified has weight 36, two above the published bound, so nothing here re-derives
the 34 independently.

## 5. Cost curve and why the search stopped

| radius R | candidates      | kernel supports | threads | search (s) | peak RSS | certifies |
|---------:|----------------:|----------------:|--------:|-----------:|---------:|:----------|
| 20       | 888,092,119     | 85,951          | 16      | 3.56       | —        | `d >= 22` |
| 22       | 7,565,506,294   | —               | 16      | 32.79      | 23.0 MiB | `d >= 24` |
| 22 (new) | 7,564,961,027   | 397,830         | 16      | 46.19      | 24.1 MiB | `d >= 24` |
| 24 (new) | 64,829,100,653  | 1,882,519       | 16      | 362.17     | 24.0 MiB | `d >= 26` |
| 26 (new) | 558,568,952,722 | 8,973,372       | 18      | 4,305.49   | 24.2 MiB | `d >= 28` |

Rows 1 and 2 are the 2026-08-29 runs; the rest are this task's.

The candidate count grows by a strikingly stable factor per two units of radius:
8.52 from 20 to 22, 8.57 from 22 to 24, and 8.62 from 24 to 26. Peak resident
memory is flat at roughly 24 MiB across the whole range, so memory is nowhere
near being the constraint — this search is bounded purely by time.

Extrapolating the same factor, radius 28 needs about `4.8e12` candidates. The
radius-26 run consumed 38,749.5 core-seconds, which is 69.4 ns per candidate per
core, so radius 28 costs roughly 334,000 core-seconds. On this 24-core host that
is about 3.9 h at perfect scaling and about 5.8 h at the parallel efficiency
actually observed. **That is why the search stopped at radius 26**: a single
radius-28 chunk exceeds the task's whole wall-clock budget by at least a factor
of two, and `css_distance_native` offers no way to split one radius across
separate invocations.

Parallel efficiency is itself worth recording, because it is the lever that would
make radius 28 reachable. The 2026-08-29 radius-22 run reached 1,375% CPU on 16
threads; this task's runs reached 997% (16 threads, radius 22), 1,155% (16
threads, radius 24) and 900% (18 threads, radius 26). The degradation tracks
contention on the shared host rather than the radius, so a radius-28 attempt
should be given a quiet machine and all cores. The input declares only two
coordinate-orbit anchors and the README describes `--threads` as a static
partition of anchors across workers, so the observed 9-11x speedups also show the
search subdivides well below the anchor level. `--rounds` reuses the compiled filter within one process,
and `--compiled-out` checkpoints only the filter, never search progress, so a
long radius must run as one uninterrupted process.

One further regularity in the same table: `kernel_supports` grows by only about
4.7 per two units of radius (4.63, 4.73, 4.77) while candidates grow by 8.6, so
the fraction of explored candidates that reach a kernel support is steadily
falling. The pruning is getting relatively more effective as the radius rises,
which is the opposite of what a naive cost model would predict and is the reason
the extrapolation above should be read as an upper estimate.

   next to the distance discussion, with the exact feature list.
2. **Compiled filter artifacts do not survive a core revision.** The 2026-08-29
   artifact `hx-gz-v3.ergocsl` now fails with `compiled CSS artifact has an
   invalid magic or version`. The fingerprint check is source-bound and works,
   but the container version moved. On this instance recompiling costs 1.5 s so
   nothing was lost, yet the artifact is advertised as a checkpoint and on a
   larger instance the loss would matter. Encoding the format version in the
   suggested filename, or accepting old versions read-only, would fix it.
3. **There is no way to split one radius across invocations.** This is the
   binding constraint on this task. `--rounds` reuses the compiled filter inside
   one process and `--compiled-out` persists only that filter; neither records
   search progress. A flag exposing an anchor range or a DFS-prefix range would
   turn a ten-hour radius into chunks that survive a session boundary and could
   be spread across machines, and it would make the exhaustion independently
   re-runnable in pieces by a reviewer.
4. **`css_distance_random` is plain Prange and is not competitive at this size.**
   Two million trials on 756 coordinates produced nothing at weight 34, whereas
   an ordinary BP-OSD pass reached 44 in 3,262 trials. The README already calls
   it "a witness finder, not a lower-bound procedure", but it would help to say
   that it inspects single kernel basis vectors with no combination step, so its
   useful regime is small codes.
5. **Minor.** `python/generate_bb_native.py --out` is create-only, so re-running
   the provenance check requires deleting the previous file first; a `--force`
   or a "write only if identical" mode would make the check idempotent.
6. **Positive.** Peak resident memory stayed at roughly 24 MiB while the
   candidate count grew by a factor of 630, and the parallel search held about
   1,375% CPU on 16 threads. Nothing about the memory or threading behaviour was
   a limit here.

## 8. Mystery ledger

**Settled by this task.**

- *Why the exhaustion's `+2` is legitimate.* It looked like a convention. It is
  not: `binary_all_ones_functional` decides whether the all-ones vector lies in
  the row space of the physical checks, and for this instance it does, so every
  logical operator has even weight and an exhausted even radius `R` yields
  `d >= R + 2`. Recorded in section 2 so the next reader does not have to
  re-derive it.
- *Where the minimum-weight logical operator does not live.* Two exhaustive
  scans settle this. It is not supported inside either bicycle sector (the exact
  sector minima are 52 and 188, both above the upper bound 34), and it is not
  invariant under any of the 102 translations whose invariant subspace is small
  enough to enumerate (exact minimum 84 there). The cheap structured routes are
  closed, which is why the remaining work is a decoding problem.
- *Whether the claimed `Z_21 x Z_18` action is real for this instance.* Verified
  rather than assumed: both generators permute the columns of the physical check
  matrix without changing its GF(2) row space.
- *The 0.007% candidate-count drift between the 2026-08-29 and current cores at
  radius 22.* A core-side pruning change; both runs certify the same bound. The
  consequence worth carrying forward is that `candidates` is **not** a stable
  replay fingerprint across Ergodis revisions, so a reproducibility check must
  compare the certified conclusion, not the counter.

**Open, with the gate named.**

- *The distance itself.* `d` is 28, 30, 32 or 34. Closing it from below needs a
  radius-28 exhaustion, about 334,000 core-seconds, roughly 4 to 6 hours on a
  quiet 24-core host; a radius-30 exhaustion after that would cost another
  factor of 8.6 and is out of reach without the chunking flag requested in
  section 7. Closing it from above needs a witness of weight 28 to 32.
- *Why the candidate growth factor per two units of radius is so nearly
  constant, and creeping up.* 8.52, 8.57, 8.62 across three steps. A constant
  branching factor is plausible, but the slow upward drift is unexplained and it
  is exactly what decides whether radius 28 lands at the low or high end of the
  4 to 6 hour estimate. Cheap to settle: the drift is measurable from the
  existing evidence files if the same three-point fit is extended by one radius.
- *Why pruning gets relatively more effective as the radius rises.*
  `kernel_supports` grows by only 4.7 per two units while candidates grow by
  8.6, so the surviving fraction falls steadily. No mechanism is offered here.
  Owning successor: whoever next touches the enumerator's pruning model.
- *What method produced the published upper bound of 34.* Not reproduced here.
  Plain Prange (two million trials), BP-OSD in several configurations (best 44),
  exhaustive sector scans (52) and exhaustive symmetric scans (84) all fall
  short, and a generic information-set attack on the full [756, 386] kernel needs
  on the order of `1e8` iterations for weight 34, which is days. The best this
  task reached is 36, from the order-two and the `(7, 12)` order-three invariant
  subspaces, and the evidence in section 3.8 says the weight-34 operator is not
  invariant under either. So the published witness has trivial translation
  stabiliser and was found by something other than symmetry — which is the
  concrete thing to ask the source about.
- *Why two of the four order-three subgroups admit no logical operator at all,
  while the other two do.* Exact and cheap to establish, and unexplained. The
  two barren ones are `(7, 0)` and `(7, 6)`, both of which shift by 7 in the
  `Z_21` factor; the two fertile ones are `(0, 6)` and `(7, 12)`. Owning
  successor: whoever next looks at the bicycle polynomial structure.

## 9. What a successor should do

1. **Radius-28 exhaustion on a quiet host.** About 334,000 core-seconds, so 4 to
   6 hours on 24 dedicated cores, using the exact command in section 3.3 with
   `--maximum-weight 28`. Success moves the certified bound to `d >= 30` and
   leaves only 30, 32, 34. This host was contended throughout the present task by
   sibling campaign jobs holding roughly 26 cores, which is why the estimate is a
   range rather than a number.
2. **Give up on symmetry for the upper bound.** Section 3.8 tried every
   translation subgroup worth trying and the answer came back 36, with strong
   evidence that no weight-34 operator is order-two invariant and exact proof
   that none is invariant under `(7, 0)` or `(7, 6)`. Further upper-bound work
   has to attack the full kernel, which means either a serious information-set
   implementation (Stern or Dumer rather than the Lee-Brickell used here, in a
   compiled language) or asking the published source what it actually ran.
3. **A chunking flag for `css_distance_native`.** Item 3 of section 7 is the
   difference between "radius 28 is a scheduling problem" and "radius 30 is
   impossible". Worth raising with whoever owns the Ergodis core.

**Candidate discovery-track entries** (incidental, found while doing the above,
not deliverables of this task; promotion needs the normal C-ID process):

- The sector scan and the symmetry scan are generic: any code in the Ergodis
  native input format can be tested in seconds for whether its minimum-weight
  logical operator is sector-supported or translation-invariant. The already
  closed [[288,12,18]], [[360,12,24]] and [[784,24,24]] cases could each be
  characterised this way for the cost of a few seconds apiece.
- The order-two divisibility filter of section 3.8 generalises: for any code with
  a free abelian symmetry, the admissible subgroup orders are constrained by the
  divisors of the candidate distances, which cheaply narrows where a structured
  witness search should look.
