# C864 — artifact citations that do not resolve in a released library

**Lane:** `build-sys` · **Date:** 2026-08-05

**Verdict: the two banner repaths cannot be prepared as banner edits.  Hand-editing generated output
to repair its prose is forbidden; the repair is a generator change applied with its regeneration and
gate inside the base re-export window.  What is prepared instead is the check that finds the defect
class mechanically, now part of the companion exporter, and the measurement it produced: the
canonical base carries three modules citing artifact paths it does not carry, in two families rather
than one, and those three are on its published `main`.  One decision is needed
before the window, and it is not a prose decision: whether the released base carries the two
verification directories that its generated tables cite.**

## Replay

```sh
python3 -m unittest test_lean_companion_export   # in lean/scripts
```

The measurement below calls `dangling_citations` over each root's tracked files.  No Lean, no Lake,
no lock, no writes.

## Why this is not a banner edit

Both modules are generated output: the arithmetic-gluing table is a delimited block emitted by
`lean/verification/clebsch_arithmetic_gluing/generate.py`, and the scheme-Fourier module is
generated whole.  The Lean workspace rules are explicit that generated output is never hand-edited
to repair its prose — the generator is fixed and the output regenerated in the owning, validated
build window, with the generator change, every regenerated leaf, and its green subtree gate
committed atomically.  The earlier plan to "prepare the repaths" therefore reduces to deciding the
target text and proving the change is confined to it, and the target text depends on the decision
below.

## The check

`lean-companion-export.py` already refuses a candidate whose content carries private references —
local paths, task identifiers, workflow vocabulary.  It had no rule for the opposite failure: a
reference that is perfectly public, correct in the repository the module was written in, and
meaningless in the release, because the release is a module subset and the named program was never
copied into it.  A reader of the release gets a path that resolves nowhere, which is exactly what
the artifact rules require a generated table not to do — it must name its tracked generator and
schema, and the named artifact must be part of what the reader has.

`dangling_citations` reads every candidate Lean source for backticked repository-relative file
paths and reports those the candidate does not carry.  Lean modules and release metadata are exempt,
since the manifest already covers them, and a DOI is exempt because it has the shape of a path and
is not one.  Ordinary mathematics — an ideal generated by `a`, a quotient `R/I` — carries no
extension and never matches.  Findings are warnings by default and refusals under
`--strict-citations`; the flag becomes the default once the base carries what its modules cite,
rather than blocking the export replays already queued for the window.

## The measured surface

| root | files | dangling citations |
|---|---|---|
| `finitegeom` base, `main` at `ac7e4ee` | 377 | 3 |
| golden quantum statistics candidate branch, `c305d4e` | 302 | 3 |

The golden checkout is not a separate library: it is the same repository on the unmerged local
branch `candidate/golden-quantum-statistics`, with no remote branch of its own, so its three
findings are the base's three inherited by a candidate rather than a second publication.  The base's
three are on published `main`.  In both:

- `RelativeConicArcs/ClebschArithmeticGluingData.lean` cites
  `verification/clebsch_arithmetic_gluing/generate.py`.
- `RelativeConicArcs/PRSRedundancyFiveCertificate.lean` and
  `RelativeConicArcs/PRSRedundancySixSevenCertificate.lean` both cite
  `papers/beyond4_prs/supplement/CLASSIFICATION-RECORDS.json`.

The second family is new information and is not C864's to fix: those two modules cite a paper
supplement, and no released library will ever carry a `papers/` path.  Either the classification
record ships with the library under a stable path or the citation is replaced by the mathematical
content it stands for.  That belongs to the beyond-4 PRS work; C864 records it because the base
re-export is what would publish it again.

Two further modules would dangle the moment an export closure reaches them:
`RelativeConicArcs/ClebschSchemeFourierData.lean` cites five
`lean/verification/clebsch_scheme_fourier/` paths, and
`RelativeConicArcs/ClebschDoubleCosetDepthData.lean` cites three
`lean/verification/clebsch_double_coset_depth/` paths.  Neither is in the base today.  Note the
`lean/` prefix: the base's root corresponds to the monorepo's `lean/`, so those citations are wrong
in a release even if the directory ships.

## The decision the window needs

Two ways to make a released library's citations resolve:

**Carry the apparatus.**  Ship `lean/verification/clebsch_arithmetic_gluing/` and
`lean/verification/clebsch_scheme_fourier/` with the base, at the same relative paths.  Together
they are 85 KB: generator, replay or digest checker, certificate, source data, and manifest.  The
arithmetic-gluing citation then resolves exactly as written, with no generator change and no
regeneration at all.  The scheme-Fourier module still needs its five citations to drop the `lean/`
prefix, which is a generator change and a regeneration, and the same applies to the double-coset
depth module whenever it is exported.

**Drop the citations.**  Rewrite both generators to emit a banner naming the schema and the data's
hash without naming a program the release does not have.  No new content class in the base, but the
released artifact loses the pointer that makes a frozen table checkable, which is the property the
resident-family determination rested on when it kept these tables in the monorepo as human-scale
semantic source.

Carrying the apparatus is the better artifact and the smaller change, and it is what the referee
rules ask for: the reader must be able to understand, reproduce, or check the generated files with
the artifact in hand.  It does change what the public base contains — non-Lean verification
directories, which the base has never carried — so it is a decision to take deliberately rather than
inside the window.

## What the window applies, once that is settled

Under the carry option: add the two verification directories to the base export; change the
scheme-Fourier generator so its header cites `verification/clebsch_scheme_fourier/...` without the
`lean/` prefix; regenerate that module; run its subtree gate; commit generator, regenerated module,
and green gate together.  The arithmetic-gluing module is untouched.  Then turn on
`--strict-citations` for every export replay, and hand the PRS citation to its owning work.
