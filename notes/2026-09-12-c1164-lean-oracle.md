## Result

`ergodis_solution P from "source.json"` invokes an external producer and constructs
`WeightedRules.CheckedSolution P`. Its `.least` theorem gives a kernel-checked proof
of least fixedness for the caller's independently supplied formal program. The actual
example calls the C1163 native provider through the existing C ABI, obtains all 21
values after four rounds, and proves distances [0,3,2,6]. No Rust implementation,
ABI, toolchain, public export or served demo was changed. No push or message sent.

Lean authority remains `lean/WeightedRules`; toolchain is pinned to
`leanprover/lean4:v4.32.0-rc1`. This is a finite ground fixpoint oracle, not a
term-minimization engine, general-purpose theorem prover or formal verification
of the Rust compiler. It does not require Lean 4.35.

## Formal interface and implementation

- `WeightedRules.checkCertificate` in `WeightedRules.Reflection` checks exact list coverage, rounds≤scalar count,
  equality with iteration from infinity, and fixedness of all coordinates.
- `WeightedRules.checkCertificate_sound` in `WeightedRules.Reflection` proves
  acceptance implies `WeightedRules.IsLeastFixed` for the caller's formal equations.
- `WeightedRules.CheckedSolution.least` exposes the proof;
  `WeightedRules.CheckedSolution.cost_order` makes the reversed numerical order explicit.
- `WeightedRules.Oracle` parses only JSON numbers into bounded-cost literals, builds
  a `CheckedSolution P`, and discharges its acceptance field with ordinary kernel
  `decide`. Error recovery to sorry is disabled and terms containing sorry are rejected.
  External text is never parsed as Lean code. Optional `via "executable"` and
  `ERGODIS_RULE_ORACLE` select the caller's local producer.
- `WeightedRules/oracle.py` supplies the subprocess adapter. It loads the native
  library named by `ERGODIS_RULE_LIBRARY`, checks the module ABI, prepares the JSON
  source, requests a workspace/certificate, invokes independent provider verification,
  and releases objects. The executable wrapper supplies Python through Nix.
- `WeightedRules.OracleExample` contains the actual imported witness
  `WeightedRules.oracleDistance`, leastness theorem `WeightedRules.oracleDistance_least`,
  readout/round theorems `WeightedRules.oracleDistance_values` and
  `WeightedRules.oracleDistance_rounds`, and the symbolic agreement theorem
  `WeightedRules.oracleDistance_agrees` against the older internal certificate.

The theorem binds to P, never to a program substituted by the oracle. Source hash
encoding is checked, but its correspondence with relational syntax is not a Lean
hypothesis silently discharged by parsing. Source lowering still requires the explicit
commutation obligations of `WeightedRules.relational_certificate_least`. Saturation
at 4294967295 remains the declared semantics; no unbounded path optimum or explicit
path witness is asserted. In information order, leastness means the certified numerical
costs are at least those of every algebraic fixed point, excluding unsupported smaller
cyclic values. No native or external decision axiom is used.

The adapter is a synchronous local subprocess. It has no process timeout or isolation;
Lean checks the 1 MiB output limit after capture, not as an OS memory bound. Ground
kernel replay is the correctness baseline, with no scaling or speedup claim. Compiled
proof imports do not re-execute the oracle; fresh elaboration of the example does.

## Automation-engine integration question

Tavis supplied the [Lean FRO Year 4 Part 1 roadmap](https://lean-lang.org/fro/roadmap/y4-1/),
covering September 2026–February 2027. It describes SymM/verification-condition tooling,
cooperation between grind and bv_decide, quick failure, independent kernel checking,
and Python integration via Nerodia. It does not specify a named Lean 4.35 engine
registration API. The earlier 4.27 link was explicitly withdrawn and was not consulted.

Proposed integration, not implemented: expose Ergodis as a goal-directed specialized
solver. Recognize an admitted finite min-plus goal, reify its formal P, dispatch the
external evaluator, replay with the existing proved checker, and return a proof to
general automation. Add cancellation, query budgets, and certificate caching tied to
the formal problem. Surrounding equality/logic stays with general automation.

SymM/verification conditions offer a route for Macready's compiler IR: symbolic proofs
establish source/lowering obligations, while Ergodis discharges supported finite
subproblems. This connects to C1162. Ordinary proof terms fit the planned independent
kernel checking workflow, subject to actual validation when available. Nerodia may
serve Python→Lean checker orchestration; it does not itself replace the Rust ABI.

The immediate adapter proposal is one goal-directed min-plus tactic with strict
admission and clear failure behavior. No framework integration or toolchain upgrade
was performed. This user-requested discussion is not an incidental discovery or a new
allocated task, and does not reorder the programme.

Tavis clarified that grind/bv_decide are the engines in question. Division of work:
Ergodis computes admitted recursive/fixpoint results; grind combines checked facts
with surrounding symbolic hypotheses; bv_decide can handle explicitly formulated
fixed-width arithmetic equivalences. The [official tactic reference](https://lean-lang.org/doc/reference/latest/Tactic-Proofs/Tactic-Reference/)
documents code-generator trust for bv_decide, unlike the ordinary kernel reduction
used by this oracle. Adding such side lemmas therefore needs its own axiom audit;
no claim of equal trusted bases is made. Full kernel replay may dominate larger
queries; a scaling claim requires measured checker costs or a proved compact
certificate checker, not merely registration with general automation.

Tavis explicitly delegated judgment and described the automation discussion as
considerations, not a scope change. Decision: preserve the proved checker, finish
C1164, and keep C1161 next; integrate general automation around a concrete IR
obligation rather than allocating a framework project speculatively.
