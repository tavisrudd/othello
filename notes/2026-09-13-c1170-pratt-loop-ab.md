## Status

Complete. Both candidates are implemented, committed, validated and measured. The 16-byte frame
alone removes about 2 per cent of ASCII parse-stage instructions; the operand/infix fast path on
top of it removes about 21 per cent, taking the parse stage from 97.7 to 77.0 instructions per
source byte and dropping `Parser::expression` from the largest symbol in the profile to the
second largest behind the scanner. Both are keepers and both are already on `main`.

## Background

The C1170 frontend measurement report (`notes/2026-09-13-c1170-frontend-measurements.md`)
attributes 40 per cent of ASCII parse-stage instructions to `Parser::expression`, the iterative
Pratt loop in `src/rel_frontend/parser.rs`, at roughly 97 instructions per source byte. Before
this work, every operand cost a pop of a tag-0 frame, a push of a tag-1 frame and a pop of that
tag-1 frame; every binary operator additionally pushed a tag-3 and a tag-0 frame, and the tag-3
reduction pushed another tag-1 frame. Frames were 32 bytes, of which 12 were reserved.

Two candidates were implemented as separate commits and are measured separately against the same
retained control.

## Commit 1 — 16-byte continuation frame (`2efeccb`)

`Frame` became `#[repr(C)]` with `tag: u8, min: u8, pad: u16, a: u32, b: u32, c: u32`: 16 bytes,
align 4, four frames per cache line. The twelve reserved bytes are gone. `Frame::new` still takes
`u32` arguments and narrows with `debug_assert!(tag <= 8 && min <= 22)`; the continuation tag
never exceeds 8 and the binding minimum never exceeds 22 (the `.` level 21 plus one for left
associativity). The loop body binds `let min = u32::from(f.min);` once after the pop and uses it
everywhere the old code read `f.min`. The compile-time size assertion moved from 32 to 16 bytes;
`Workspace::retained_bytes` picks the new size up through `size_of::<Frame>()`. The
`analysis/rel-frontend/README.md` line that described continuations as 32 bytes now says 16.

Behaviour is unchanged. The parity replay's canonical SHA-256 stayed
`5792fd09758dc028ad191656a93556de10991bc07eec8db6234f4bad72f67b08`; only the two test-library
hashes and the `parser.rs` source hash moved in `portability-v1.json`.

## Commit 2 — operand/infix fast path (`c973737`, on top of `2efeccb`)

`Parser::expression` now runs three phases in one loop over a local binding minimum `min`, and
tags 0 (parse operand) and 1 (infix loop) no longer exist as frames.

- Phase A consumes prefix operators and openers until `self.last` holds an operand. Atoms,
  `:name` symbols and empty groups set `self.last` and fall through to phase B. A prefix operator
  pushes `Frame::new(2, min, index, 0, 0)` and sets `min = prec`; a non-empty group pushes
  `Frame::new(4, min, index, 0, 0)` and sets `min = 1`; `if` pushes `Frame::new(6, min, index, 0,
  0)` and sets `min = 1`. Each then re-enters phase A.
- Phase B is the infix loop over `self.last` as left-hand side. Spread, qualified `a:b` and the
  empty applications `f()` and `f[]` build their node inline and keep looping without pushing
  anything. A non-empty application pushes `Frame::new(5, min, lhs, index, 0)` and sets `min = 1`;
  a binary operator with `prec >= min` pushes `Frame::new(3, min, lhs, index, 0)` and sets
  `min = prec + !right`; both then go to phase A. Everything else, `prec < min` included, leaves
  phase B for phase C. The trailing-comma and semicolon-before-closer rule is unchanged.
- Phase C pops one frame. With no frame left the expression is complete and `self.last` is
  returned. Tags 2, 3, 4, 5 and 8 build their node exactly as before, set `min = f.min` and resume
  phase B. Tags 6 and 7 do their `expect`, push the next frame carrying the same `f.min`, set
  `min = 1` and go to phase A.

The invariant that makes this work: each frame's `min` field is the binding minimum to resume the
infix phase with once that frame reduces. Tags 2, 4, 6, 7 and 8 previously stored 0 there and the
tag-1 frame carried the value instead.

Node creation order, node contents, the `expression(minimum)` signature, the entry
`debug_assert!(self.w.frames.is_empty())`, the recovery path and both scanner variants are
unchanged.

The one observable difference is nesting depth. Only pending operators and openers occupy the
stack now — about one frame per nesting level instead of two plus a transient third — so a fixed
`limits.depth` admits roughly twice the nesting before `DepthCapacity`.

## Parity canonical SHA change

The fast path changes exactly one record of the 146-case parity corpus.

- Old canonical SHA-256: `5792fd09758dc028ad191656a93556de10991bc07eec8db6234f4bad72f67b08`
- New canonical SHA-256: `0625e2f1196221e4ce343526c59862ea5392424bd0782c45bb43581bcd8e75eb`

## Measurements

Method: `analysis/rel-frontend/bench.py` in candidate-versus-control mode, which measures every
operation on both binaries each round and alternates which binary goes first, under `perf stat`
with two-point differencing (`per_iteration = (counter(N) - counter(N/2)) / (N - N/2)`), seven
rounds, pinned to CPU 5. Host: AMD Ryzen AI 9 HX 370, kernel 7.0.9, rustc 1.93.1, perf 7.2.4,
release profile, no features. Candidate binaries are the retained `ergodis-tools-2efeccb`
(sha256 `0feff41a1ee1…`) and `ergodis-tools-c973737` (sha256 `a5348acf7abe…`); the control in
every run is the retained `ergodis-tools-f820daf` (sha256 `cbb7f6d63e05…`).

Instruction ratios decide. Cycle ratios are reported with their intervals and are noisy: another
session was building and running tests on the same box throughout, so the one-minute load average
sat between 6 and 20 during the measurement window. Instruction counts are unaffected by that;
cycle counts are not, and several cycle intervals below straddle 1.0 and settle nothing.

All three receipts are committed under `analysis/rel-frontend/`. The driver also verified, before
computing any ratio, that candidate and control produce the same token/node fingerprint on every
operation; it aborts otherwise. I separately confirmed that all three binaries agree on
fingerprint, token count, node count and failure identifier on all five cohorts.

One driver limitation surfaced here. `bench.py` builds its A/A null pair by name from the `parse`

parse,recover`. This is recorded in the README rather than patched, since changing the driver
mid-measurement would have invalidated the receipts already taken with it.

## Mystery ledger and unexpected observations

Erratum: the commit message of `c973737` says a fixed `limits.depth` reaches "about three times
the nesting". The correct factor is about two: the old loop held two persistent frames per open
parenthesis (the tag-1 continuation and the tag-4 opener) plus one transient tag-0 frame; the new
loop holds one. The report and the parity evidence (byte 269 → byte 526 for depth 512) carry the
correct figure; the commit message is left as written rather than rewriting history.

The `prepare` stage is about 1.2 per cent more expensive on both candidates than on the control:
1.0120 [1.0044, 1.0197] for the frame change, 1.0126 [1.0061, 1.0192] for the fast path, 1.0137
[1.0078, 1.0197] in the recover run. The intervals exclude 1.0 in all three. `prepare` only
allocates and drops a `Workspace`, and the candidates reserve strictly less memory than the
control, so the parser changes cannot explain it. The likely cause is the provenance caveat above:
the control was built from a different state of the surrounding crate, so code layout differs, and
`prepare` is only about 2,500 instructions — small enough for layout to move it by a per cent. It
is consistent across all three receipts and immaterial to the parse-stage result, which is two
orders of magnitude larger, but it is not explained and it is the visible evidence that these
executables differ by more than the parser diff. Settling it would need a control rebuilt from
`d761aa0`, the commit immediately before candidate A, which would cost one more retained binary
and one more seven-round run.

Branch misses and cache misses come out of the two-point differencing as counts in the hundreds
per iteration, including one negative value (−90 cache misses per iteration on the candidate-A
ASCII row). At that magnitude the difference of two multiplexed counters is pure noise and neither
event says anything here. Instructions, cycles and branches are the usable events.

The `analysis/rel-frontend/README.md` paragraph on the parity replay says the corpus has 142
cases, while `portability-v1.json` records 146. The count is stale rather than wrong in kind, and I
left it alone rather than churn an unrelated line during a measurement task.

## Remaining next steps

1. The scanner is now the majority of the parse stage: `lexer::scan` at 47.75 per cent and
   `lexer::keyword` at 8.54 per cent against `Parser::expression` at 39.41 per cent. The keyword
   lookup is a linear `match` over 32 string literals per identifier and is the obvious next
   target; a length-bucketed or perfect-hash dispatch should take most of its 6.6 instructions per
   byte.
2. `Parser::expression` still costs about 30 instructions per source byte. What remains is one
   frame push and pop per pending operator and opener plus the node writes. The next structural
   step would be keeping the pending operator in registers for the common right-associative chain
   rather than in the frame pool, which is a larger change and should be Fermi-estimated first.
3. The cold-start boundary from the earlier C1170 report is still open: `prepare` does not charge
   first-touch page faults, so a fresh or resized workspace's real cost is unmeasured. The
   unexplained 1.2 per cent `prepare` difference above is a second reason to build the
   `prepare-touch` stage.
4. The depth budget changed meaning. A given `limits.depth` now admits roughly twice the nesting,
   which is a user-visible capacity change even though it is strictly more permissive. If the
   default 512 was chosen to bound worst-case stack work rather than to bound accepted inputs, it
   could be halved to restore the old accepted-input boundary at half the memory.
