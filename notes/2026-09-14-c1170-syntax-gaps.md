## Reference findings, family by family

### Caret-prefixed entity references

The documentation page is explicit about the lexical shape and silent about the ambiguity. From
`rel-ref-lexical.txt`, lines 317–319 and 331–335:

```
Identifier := ("^")? IdCharInit IdChar*
IdCharInit := [a-zA-Zα-ωΑ-Ω_]
IdChar     := [a-zA-Zα-ωΑ-Ω_0-9]
```

> The optional caret character `^` can appear only at the beginning of an identifier. Identifiers
> beginning with a caret are used for naming some relations that are automatically generated by
> Rel.

The pinned editor grammar splits that into two tokens, `syntax.grammar` lines 425–427:

```
basicIdentifier { idCharSingle | idCharInit idChar+ }
BasicId { basicIdentifier }
ConstructorId { "^" basicIdentifier }
```

and it also lists `"^"` as an alternative of the `Operator` rule (line 431, the rule opening at 429)
and uses it as the exponentiation infix at line 267,
`BasicExpression !power op<"^"> BasicExpression`. The one line that speaks to the conflict is
the token-precedence declaration at line 549, `@precedence { ConstructorId Operator }`: a Lezer
token precedence is needed exactly when two tokens can match in one parser state, and it says the
constructor wins there. The grammar's own test corpus exercises only the constructor reading —
`Identifiers.test.txt` line 36 `def ^b = ^B[1, 2]` parsing to `LhsId(ConstructorId)` and
`BasicExpression(ConstructorId)`, and lines 109 and 111 `def ^Constructor:abc = 4` and
`def rel:^Constructor = 6` parsing through `QualifiedNameElem`, which is
`":" (BasicId | ConstructorId) | …` at line 534. **No test in the corpus writes `a^b`**, so the
reference set fixes the constructor reading, fixes that `^` is also the power operator, and never
shows the two in one source.

Read purely lexically, that precedence makes `a^b` scan as `a` followed by the constructor `^b`,
which no grammar production accepts — and C1171 had already repaired unspaced identifier
exponentiation here, with a committed regression. A Lezer parser does not in fact read it purely
lexically: its tokenizer is masked by the LR state, so the constructor reading is available only
where an operand may begin. That state distinction is the rule adopted below.

### String interpolation

`syntax.grammar` lines 208–215 and 535:

```
interpolation
    { InterpolationId
    | InterpolationExpression
    }

InterpolationExpression { "%(" v1expression ")" }

InterpolationLiteral {
    quote1 staticStringPart? interpolation (staticStringPart | interpolation)* quote1
}

InterpolationMultilineLiteral {
    quote3 staticMultilineStringPart? interpolation (staticMultilineStringPart | interpolation)* quote3
}
...
InterpolationId { "%" basicIdentifier }
```

The literal-part tokens exclude the sign outright, lines 514–515:
`staticChar { !["\r\n\\%] }` and `multiStaticChar { !["\\%] }`, while `EscapeChar` (line 503)
admits `'\\' '%'`. So an unescaped `%` inside a plain or triple-quoted string **must** open an
interpolation, and `\%` is the literal character. `InterpolationId` is a token in its own right, not
a `BasicId`, so the keyword specializations (`kw<term> { @specialize<BasicId, term> }`, line 566) do
not reach it.

`rel-ref-constants.txt` confirms the same rules in prose and adds the boundaries the grammar does
not state: line 516, "since their contents are taken literally, raw strings do not support string
interpolation"; line 495, "`raw"ab%c"` is equivalent to `"ab\%c"`"; lines 520–521, interpolation is
allowed "as long as the latter is not a raw string and does not occur in the head of a definition";
line 530, "In the case of a simple identifier, the parentheses may be omitted"; and line 553,
"Interpolation can be nested", with the example
`def output = "Hello %(from_id["user_%nums"]) and bye"`, which is a string inside the expression of
an interpolation of another string. Character literals are `CharLiteral { "'" ( !['\\] | EscapeChar ) "'" }`
(line 540) and carry no interpolation, and `DocstringLiteral` (line 525) is
`quote1 (!["\r\n\\] | EscapeChar)* quote1`, which admits a bare `%`.

### Unicode boundaries

The lexical page's identifier classes are the three lines quoted above, and the page immediately
undercuts them, lines 325–326 and 337–340:

> For example, valid identifiers are: `x`, `a1`, `b1c`, `θ`, `φ`, `Σ`, `ß`, `β1`, `β2`, and `^V`.

> Due to missing features in the parser generator, the definition explicitly lists supported ranges
> of Unicode letters (hence the Greek ranges). This is currently incomplete, so Rel does not yet
> support other Unicode letters in identifiers.

`ß` is `U+00DF`, which is in none of `[a-zA-Zα-ωΑ-Ω_]`, so the example list and the production
contradict each other and the page says which way the error runs: the ranges are the incomplete
side. The editor grammar repeats the same three classes verbatim (`syntax.grammar` lines 416–425)
and adds what the documentation page never states — the whitespace, newline and operator sets, lines
413–414 and 480:

```
spaces[@export] { $[\u0009 \u000b\u00a0\u1680\u2000-\u200a\u202f\u205f\u3000\ufeff]+ }
newLine[@export] { $[\r\n\u2028\u2029] }
...
Operator { ... | $[\u2200-\u22FF] }
```

Three facts follow that the prototype did not have. `U+FEFF` is whitespace although its Unicode
`White_Space` property is `No`. `U+000C` and `U+0085` are in neither set although
`char::is_whitespace` accepts both. And the whole Mathematical Operators block is an operator, where
the prototype carried a hand-written list of thirteen spellings from it.

## The adopted contracts

Each of these is **this stage's stated contract, not a claim about Rel.** The lane has no executable
Rel reference semantics, the reference set is internally contradictory on two of the three
questions, and the third — how `a^b` and `^Person` are told apart — is answered in the reference set
only by a token-precedence declaration whose effect depends on the parser generator's state
masking.

### 1. A caret is the power operator after an operand and an entity reference everywhere else

A `^` immediately followed by an identifier-start character is one `Kind::EntityRef` token spanning
the caret and the identifier, **unless** the token before it ends an operand, in which case it is
the infix power operator as before. A token ends an operand when its kind is `Name`, `Number`,
`String`, `RawString`, `StringClose`, `Character`, `EntityRef`, `True`, `False`, `Underscore`,
`End`, `Ellipsis`, `RParen`, `RBracket` or `RBrace`. `StringClose` — the closing quote run of an
interpolated literal, which ends an operand exactly as a plain string token does — joined the set at
`fe4fda7`, after the interpolation family existed to produce it. This is the LR state distinction, decided in the scanner from one
look at the previous token, which is read only at a caret.

Consequences, all covered by fixtures: `a^b`, `a ^b`, `a^ b`, `a^2` and `(1)^b` exponentiate;
`^Person`, `(^E)`, `f(^Person)`, `^_x`, `-^E` and `:^Foo` are entity references; `^E^2` is
`(^E) ^ 2` because an entity reference ends an operand; `x^^y` is `x ^ (^y)` because the second
caret follows an operator. A caret that opens nothing — `^`, `^1`, `^ E` — stays the power operator
and fails as `ExpectedExpression`.

Two cases that look like widenings are not. No keyword lookup runs on the identifier after a caret,
so `^end` is an entity reference and not the keyword — and that conforms, because the keyword
specializations are `@specialize<BasicId, term>` and `ConstructorId` is a token in its own right,
the same argument the interpolation section makes for `InterpolationId`. And `^_x` conforms too:
`idCharInit` is `[a-zA-Zα-ωΑ-Ω_]`, so `_x` is `idCharInit idChar+` and `^_x` is a `ConstructorId`.

Two widenings are real and recorded. The identifier after the caret uses the ordinary identifier
classes rather than `basicIdentifier`, so a lone underscore is accepted — `^_` is an entity
reference where `basicIdentifier`'s single-character alternative is `idCharSingle
{ $[a-zA-Zα-ωΑ-Ω] }` and excludes it — and the widened letter class of family 3 reaches the caret,
so `^ß`, `^Σ` and `^格子` are entity references where the reference's ranges admit only `^Σ`.

**Binding.** An entity reference parses to `NodeKind::Entity` and admission resolves it as a name
whose spelling includes the caret. It is global, it may head a definition (`def ^b = ^B[1, 2]`, the
reference corpus's own case), its arity is fixed by its first application like any external base
relation, and it is **never a binder**: no binder list accepts one, so `def f(^x) = 1` is
`UnsupportedSemantics`, and because the caret is part of the spelling, `^x` and a binder `x` are
different names and neither shadows the other. That is the simplest rule that keeps the existing
binding and arity contract intact — the only admission code that knows about entity references is
one traversal arm, one declaration arm and one applied-callee test.

### 2. Interpolation is scanned as parts and parsed through one more continuation frame

An unescaped `%` inside a plain or triple-quoted, non-raw string opens an interpolation. The scanner
stops emitting the literal as one token and emits instead `Kind::StringOpen` for the opening quote
run, `Kind::StringPart` for each run of literal bytes, `Kind::Name` for a `%name` — span excluding
the `%`, no keyword lookup, matching `InterpolationId` — `Kind::InterpolationOpen` for `%(`, and
`Kind::StringClose` for the closing quote run. The parser builds a left-nested
`NodeKind::Interpolation` chain: `a` is the chain so far, `b` is the piece, and the last link is the
literal's root and spans the whole literal.

A `%( … )` expression is parsed by the existing iterative Pratt loop through one new continuation
tag, so an interpolation costs one bounded frame and nothing on the Rust stack; a string inside such
an expression opens a new scanner level, bounded by a fixed eight-entry array. Raw strings and
character literals never interpolate, which the reference states outright for raw strings and which
follows from `CharLiteral` for character literals; `\%` is the literal sign.

Rejections, all with stable identifiers and exact spans: a `%` followed by neither an identifier
start nor `(` is `MalformedInterpolation` (`REL0105`); nesting past the eighth open literal is
`InterpolationDepth` (`REL0106`); a literal or an interpolation the source ends inside is
`UnterminatedString` (`REL0102`), reported against the opening quote of the literal that is still
open. Inside a `%( … )` a quote opens a nested string, so `"%(1"` is unterminated at the **inner**
quote, which is an instructive negative rather than a defect.

Admission binds names inside interpolations in both forms, and an escaped one is `UnboundName` like
any other use. An interpolated literal in a definition head is `UnsupportedSemantics` — but that
rejection **subsumes** the reference's rule rather than implementing it: a definition head holding
any literal is rejected the same way at the same span, so `def f["a"] = 1` fails exactly as
`def f["%x"] = 1` does. The stage declares names, and a head that is not a name is a form it does
not understand.

One divergence is recorded rather than implemented: the scanner cannot tell a doc string from an
ordinary one, because scanning precedes parsing, so `doc "100% sure"` is `MalformedInterpolation`
here although `DocstringLiteral` admits a bare `%`. Nothing that used to be accepted is now
rejected by it — a `%` in a plain string was `UnsupportedSyntax` before this task.

### 3. Identifier classes take the reference's prose for letters and its grammar for digits

`IdCharInit` is `_` or a character with the Unicode `Alphabetic` property. `IdChar` is that or an
**ASCII** digit. Whitespace is `char::is_whitespace` plus `U+FEFF`. The whole Mathematical Operators
block `U+2200`–`U+22FF` is an operator, with the spellings that already had a kind keeping it and
the rest becoming `CustomOp`.

The letter side takes the prose because the page says the ranges are the incomplete side and its own
example list breaks them; `Alphabetic` contains `[a-zA-Zα-ωΑ-Ω_]`, so "at least Rel richness" holds
and `ß`, `Ⅷ`, `ａ` and CJK names are accepted extensions. The digit side takes the grammar, and the
asymmetry is deliberate: the page's "currently incomplete" remark is about the *letter* ranges and
nothing else, and where the prose speaks to continuation at all it says only "zero or more Unicode
letters, underscores, or numbers", which names no class. The one precise digit class in the
reference set is `IdChar`'s `0-9`, in both the documentation production and the editor grammar, so
that is what continues an identifier here: `char::is_numeric` had been continuing them, which glued
`½`, `²`, `₁`, `٣` and the full-width digits onto a name. That is the one narrowing in this task, and it is a narrowing towards
the reference.

`U+FEFF` is added because the grammar's `spaces` token lists it and `White_Space` does not.
`U+000C` and `U+0085` are kept although the grammar lists neither, as a superset. A one-character
`_` stays the anonymous variable rather than an identifier, which is what
`basicIdentifier { idCharSingle | idCharInit idChar+ }` says, and `__` and `_1` are identifiers.

**One divergence is open.** `Alphabetic` includes `Other_Alphabetic` combining marks, so `U+0903`
and `U+093E` start an identifier here; neither the reference's `IdCharInit` nor UAX #31's
`XID_Start` allows that. The exact rule wanted is `XID_Start`/`XID_Continue`, which needs a Unicode
general-category or identifier table; `core` has none, and the native/WASM parity harness compiles
the frontend with bare `rustc` and no `--extern`, so a crate such as `unicode-ident` cannot be taken
without rebuilding that harness. Recorded in the coverage manifest as the lexical family's one
remaining item. A combining mark that is not `Other_Alphabetic`, such as `U+0301`, neither starts
nor continues an identifier, which conforms to the reference and diverges from UAX #31 the other
way.

Out of scope and left to their families, with the manifest wording updated to say so: complex
escapes (`\xNN`, `\uNNNN`, `\UNNNNNNNN`, octal), radix literals, numeric separators, typed
constants, date and datetime literals, normalization and value decoding. None of them is silently
implemented; each still rejects explicitly.

Structurally, `"a%(1+2)b"` is checked to be a two-link chain whose root spans bytes 8 to 18, whose
pieces are a literal part, a `Plus` expression and a literal part, and whose first link has `a` of

## Fermi predictions, written before the measurements

The unit counts come from a census of the ASCII cohort's 43,008 bytes: 128 carets, about 960
compound-lead punctuation tokens (`<`, `>`, `+`, `:`, `^`), 6,464 single-byte punctuation tokens,
7,872 whitespace bytes, 15,489 tokens and 12,288 nodes. The control's ASCII parse stage is about
2,507,800 instructions and its ASCII admission stage about 1,246,700.

**Caret entity references (`80f3305`).** The caret leaves the single-byte punctuation path for the
compound-lead branch, so each of the 128 carets pays one class-bit test, a call to
`entity_reference` that decodes the next character and finds it is not an identifier start, and an
empty compound loop — about 15 instructions more than the table store it had. The other roughly 830
compound-lead tokens pay one `test`-and-branch each. Predicted parse **+3,600, ratio 1.0014, band
1.001 to 1.003**. In admission the applied-callee test gains one comparison per application, about
1,600 of them, predicted **+3,200, ratio 1.0026, band 1.002 to 1.004**. No pool changes, so

## Method

Event set `instructions,cycles,branches,branch-misses,page-faults,minor-faults`, six events, no
multiplexing: a direct `perf stat -x,` on each candidate's ASCII admit stage reports 100.00 per cent
enabled on all six. Seven interleaved rounds, all five cohorts, both scanner variants,
`--stages prepare,prepare-touch,parse,admit`, 512 definitions, pinned to CPU 5, the driver's output
gate armed on every operation. Host is an AMD Ryzen AI 9 HX 370, kernel 7.2.4, `perf_event_paranoid`
2 so only user-mode events are counted. Instruction ratios decide; cycle ratios are quoted with their
intervals and settle nothing alone. The box was shared throughout with another user process at
roughly one and a half cores, load average 2 to 10 across the runs, which widens cycle intervals and
leaves instruction counts alone.

No `--representation-change` declaration was needed or passed: tokens, nodes, failures, the admission
summary and the representation fingerprint are equal on every operation of every run.

## Shape repair

Four repairs follow from that diagnosis, all of them about compiled shape rather than about the
features. They were built together as `f7337c4` and measured against `d1f24ba`; the next section
gives the verdict, which is that two are kept and two are losses reverted by `e8b4c7c`.

1. **The parser's entity-reference arm is merged into the leaf-operand arm.** `Kind::EntityRef`
   joins the `Kind::Name | … | Kind::Underscore` arm and chooses its node kind in an expression, so
   `Parser::node` has one call site for every leaf operand again instead of two.
2. **Admission's entity arm is merged into the atom arm.** `NodeKind::Atom | NodeKind::Entity` share
   one `reference` site; because `reference` is `#[inline(always)]`, a separate arm had duplicated
   the whole resolution body inside `admit::run`. A bare name still short-circuits on the first
   comparison.
3. **The caret's two cheap tests are hoisted to the call site and the interpolation's paren step is
   inlined.** `caret_opens` is `#[inline(always)]` and decides from the class table and the previous
   token, so `entity_reference` — now just the identifier scan — is called only by a caret that
   really opens one. `interpolation_paren` became an `#[inline(always)]` predicate over the level
   array, so the scan loop's punctuation branch holds a comparison and a fall-through instead of a
   seven-argument call.
4. **The byte-order mark and the operator block move off the character dispatch.** Both tests now
   sit in the fall-through arm of the `match c`, which is the path that was already about to raise
   `UnexpectedCharacter`, instead of in the whitespace predicate and as a range arm of the dispatch
   itself. Nothing about the accepted language changes: a byte-order mark still skips as whitespace
   and `U+2200`–`U+22FF` is still an operator; only the order in which the scanner asks reaches
   them.

## Instructive negatives

1. **A per-unit Fermi cannot price a change that adds a call site or a loop-carried local to an
   already register-tight loop.** All three families' predictions were within a factor of two of the
   executed work they add and out by three to twenty-three times on the measurement. The scanner's
   loop keeps the source pointer, the cursor, the token slice, the write cursor, the class byte and
   the previous position live; the parser's keeps the workspace, the position, the last node and the
   binding minimum. Adding one more live value or one more call site to either costs two to four
   instructions per unit across the whole loop, which dwarfs the feature's own arithmetic. The
   correction is the same one the module-scope report reached from the other side: **diff
   `nm --size-sort -S` and the loop's disassembly before writing the prediction, not after**.
2. **The comment-string cohort is the cheapest available control for "is this cost the feature?"**
   It contains no caret and no per cent sign, so any movement it shows under a caret or interpolation
   candidate is layout. It showed +22,148 and +18,709. Reading it first would have saved a round.
3. **A predicate that every character reaches is not a cheap place for a rare test.** One
   `c == '\u{feff}'` added to the whitespace test cost 4.5 per cent of the comment-string cohort's
   parse stage. The same acceptance, asked in the fall-through arm of the character dispatch, is free.
   The Fermi called this out in advance and the measurement confirmed it, which is the one prediction
   in this task that earned its keep.

## Mystery ledger

1. **Settled.** Why the caret family cost twenty-three times its Fermi. It is not the caret path:
   the comment-string cohort contains no caret and moved +22,148 anyway. Settled by that cohort, by
   the malformed-early proxy splitting the cost across scanner, parser and admission, and by
   `nm --size-sort -S`, which shows all three loops larger and `lexer::entity_reference` out of line.
2. **Settled.** Why interpolation cost five times its Fermi. Same mechanism, and the symbol table
   adds the sharp form: between `80f3305` and `1cc34ae` the scan loop crossed the inliner's
   threshold and `lexer::scan` stopped being folded into `Workspace::scan_variant`.
3. **Settled.** Whether the scanner's share read off the `malformed-early` cohort is the scanner.
   The driver's own `scan` stage, measured directly at both ends, gives +105,221 against the proxy's
   +105,012 on the byte scanner and +94,540 against +94,368 on the scalar one.
4. **Settled.** Whether the new code put a call into the hot loop. The kernel-scoped profile shows no
   libc, allocator, formatting or panic symbol inside the scan loop at either end; the only other
   symbols are `lexer::keyword`, a leaf, and one `from_utf8` outside the loop.
5. **Settled, and it is the one repair kept.** Why the Unicode family cost 4.5 per cent on the
   comment-string cohort and 0.5 elsewhere. One `c == '\u{feff}'` in the whitespace predicate, which
   that cohort reaches for every quote, comment slash and dot. Moving it to the fall-through arm of
   the character dispatch recovered 3.5 per cent there and 0.3 on Unicode.
6. **Open.** The interpolation candidate made the ASCII admission stage 6,320 instructions
   **cheaper** while making the parse stage 65,961 dearer, and it touches no admission code at all.
   Layout is the presumption and there is no evidence for it beyond the sign. The gap is a
   disassembly of `admit::run` at `80f3305` against `1cc34ae`; the symbol is 6,430 bytes at both, so
   whatever moved is inside it.
7. **Open.** The byte and scalar scanners disagree by more than a factor of two on which family
   costs them what — interpolation is 2.5 per cent of the ASCII byte parse stage and 1.3 of the
   scalar one, and on comment-string the order reverses at 1.3 against 3.7. Both variants execute
   the same new guards the same number of times. The gap is a per-region `perf annotate` of the two
   scan symbols; `analysis/rel-frontend/annotate-buckets.py` already does the bucketing and was not
   run here.
8. **Open.** Of the Unicode family's +14,242 on the scan-only cohort, the byte-order-mark repair
   recovered none, although it recovered the whole of the comment-string and Unicode costs. What
   remains is the `is_numeric`-to-`is_ascii_digit` change and the operator dispatch's new
   fall-through arm, neither of which the ASCII cohort executes. Same evidence gap as item 7.
9. **Settled, negative.** Whether giving the two new leaf kinds the existing call sites is cheaper
   than duplicating them. It is not, in either loop: +30,143 in the parser and +57,458 in admission.
   Both reverted by `e8b4c7c`.

No item on this list is manufactured; items 6, 7 and 8 are three faces of one unmeasured quantity,
which is where inside the two scan symbols and `admit::run` the added instructions sit, and one
`perf annotate` pass over named address ranges would close all three.

## Remaining gaps

1. **`XID_Start` conformance for combining marks.** A combining mark with the `Other_Alphabetic`
   property starts an identifier here. `core` carries no general-category table, and
   `analysis/rel-frontend/portability.py` compiles the frontend with bare `rustc` and no `--extern`,
   so `unicode-ident` cannot be taken without rebuilding that harness. Recorded in the coverage
   manifest's `lexical` family. The next step, if it is worth taking, is to decide whether the parity
   harness should link a dependency at all.
2. **Interpolation inside a doc string.** The reference's `DocstringLiteral` admits a bare per cent
   sign; scanning precedes parsing here, so `doc "100% sure"` is `MalformedInterpolation`. Nothing
   that was accepted before is rejected now — a per cent sign in a plain string used to be
   `UnsupportedSyntax` — but the reference does accept it. Closing it needs the scanner to know it is
   inside a doc item, which is the contextual-token mechanism the keyword work already uses for
   `doc`, `value`, `type` and `declare`.
3. **The `literals` family's remaining items are untouched and still reject explicitly**: complex
   escapes (`\xNN`, `\uNNNN`, `\UNNNNNNNN`, octal), radix literals, numeric separators, typed
   constants, date and datetime literals, normalization and value decoding. Date and datetime
   literals, which the grammar has and the prototype does not, were implicit until `b51f627` named
   them in the manifest.
4. **A feature-presence monomorphization is the untaken lever, and it is larger than interpolation.**
   The immediate form is a second const generic on `scan_into`: the first pass runs with
   interpolation compiled out and is the pre-feature loop, and the first per cent sign inside a
   string restarts the scan in the interpolating mode. Sources without interpolation would then pay
   nothing at all rather than the measured per-token guard, at the cost of four copies of the scan
   loop and one rescan of the prefix for sources that do interpolate.

   The general form is worth stating because this task is the second piece of evidence for it. Every
   lexical feature the prototype adds is a run-varying test in a loop where a run-varying test costs
   two to four instructions per token whether or not it fires, and most sources use almost none of
   the features. A single cheap byte-class prepass over the source — which the scanner already has
   the tables for — can produce a presence bitmask (interpolation, entity references, raw strings,
   non-ASCII, block comments) and dispatch once, outside the loop, to a monomorphization that has
   only the features the source actually contains. That is the hot-loop rules' own
   "run-constant decisions are made once, outside the loop", applied to a quantity that is not
   constant across runs but is constant within one, and it converts the whole family of future
   syntax additions from a per-token tax into a prepass. It is not built and not measured, and its
   cost — code size across the variant lattice — is exactly what would have to be measured first.

## Audit corrections (2026-09-15)

An independent verification pass re-ran the gates and re-derived every measured claim in this
report; it is written up in `2026-09-15-c1170-syntax-gaps-audit.md`. The measurements all stood: the
seven retained binary hashes, all five A/B receipt tables, the symbol-size table, the kernel-scoped
profile shares, the representation invariants across all seven binaries, the direct scan-stage
corroboration, the foreign-diff hash, and the 193-case parity corpus, which regenerated with the
same canonical SHA-256 and the same compiled library hashes. A replay of the composed A/B on
2026-09-15 reproduced 1.065117 [1.065116, 1.065119] on the ASCII parse stage and 1.095627 against
the receipt's 1.095625 on the scan-only cohort, with A/A nulls inside three parts per million.

Eleven text defects were found and are corrected above. The substantive ones: the claim that none of
the cost is the features executing was true of the caret and interpolation families and not of the
Unicode family, whose cohort carries 2,048 identifier characters outside the reference's letter
classes and whose repaired byte-order-mark term was executed work; the two recorded "widenings of
`ConstructorId`" (`^end` and `^_x`) are both conformant to the pinned grammar, and the real
widenings are `^_` and a caret over the widened letter class; and the definition-head rejection
subsumes the reference's interpolation rule rather than implementing it, since a head holding any
literal is rejected identically. The smaller ones: the operand-ending kind list was missing
`StringClose`; the per-commit parity-row counts were swapped and one was short; a remaining gap
asked for date and datetime literals that `b51f627` had already added to the manifest; the
digit-class justification passed over the lexical page's "letters, underscores, or numbers" prose;
three reference line citations were off by a few lines; the caret Fermi's application count and the
singular description of `lexer::entity_reference` were imprecise; and peak resident set is not
unchanged but about one per cent lower in the candidate.

Two code repairs followed, committed to the private repository as `837c441`: the caret fixture's
cases now all run through a two-variant helper that compares tokens and nodes, so this report's
statement that every case in the three tests is checked on both scanner variants is now true of the
caret test as well; and the interpolation fixture's definition-head case, which previously asserted
only that `def f = 1` admits, now asserts `UnsupportedSemantics` for `def f["%x"] = 1`,
`def f("%x") = 1` and `def f["a"] = 1`. The parity corpus is untouched by both, so its canonical

regression, strict Clippy and `rustfmt --check` all pass after the repairs.
