** DONE Fix the format and trust boundaries

Owner: primary design and review. The existing =finite-boolean-ranked-certificate.v1= JSON, its source identity, checker verdicts and digest stay byte-for-byte compatible. Rank runs are a separate, opt-in JSON certificate schema over the same claim: each relation retains its original tuple stream and replaces one rank per tuple with strictly increasing positive =(rank,count)= runs. The evaluator already appends derived rows in non-decreasing round order, which is the producer obligation. A run with zero count or a total different from the tuple count is malformed; the checker must not infer ranks from position alone.

The binary form has its own versioned schema and canonical bytes. Its header binds the literal schema and =source_id=. Each relation has strictly increasing rank runs encoded as positive rank differences and counts; the binary encoder alone sorts each run's packed tuple keys and uses either shortest-form LEB128 first-key/gap-minus-one values or a full-universe bitmap. The deterministic choice is the shorter payload, ties to gaps. Decoder admission must refuse truncation, trailing bytes, nonminimal varints, zero or decreasing runs, rank overflow, key overflow/out-of-universe, duplicate keys within a block, nonzero bitmap padding and a noncanonical coding choice with named errors. The admitted source supplies domain, arities and relation count; no certificate-supplied geometry is trusted. The byte bound is checked before parsing and every count is bounded by the remaining bytes before allocation. At domain 65,536 and arity four, the mathematical universe is exactly =2^64= while the stored =u64= universe saturates to =u64::MAX=; packed key =u64::MAX= is valid. The codec must compare in =u128= or validate by unpacking, and exclude this universe from bitmap selection.

The independent checker will read binary blocks into its existing relation store and rank columns, then run the existing support search and separate closed-world completeness pass. It must not materialize a v1 =RankedCertificate= or JSON. A sorted-store fallback may require one bounded parse to collect keys and a second to insert them; both parses enforce the same canonicality. Verification records bind =(new certificate schema, digest of canonical binary bytes)= and the checked source/output, using the existing separate contract and checker identities. The ordinary evaluator, old JSON route and visible relation output incur no new work until the caller opts into a compact certificate.

Adding contract/checker source necessarily moves their implementation identities, so old verification records do not replay across the build change; the record schema remains unchanged and a fresh successful check issues a new record. The old v1 JSON certificate's canonical bytes and digest must remain identical. A compact certificate's rank run order is per relation and its tuple order is per run, so the checker must compare ranks by value rather than global listing position.

Fermi before implementation: C1185 measured the rank column at 8–107 bytes over its largest row streams when run coded, versus one byte per tuple; round blocks cost 0.250–1.064 payload bytes per derived tuple on its eleven rows, versus 5.000 packed or 11.50 JSON bytes on the cited large closure. The cost is cold sorting/encoding, measured at 222.8 ms versus 520.8 ms evaluation on sparse closure 4096 in the old prototype. This predicts a large transfer-size win and a nontrivial opt-in producer cost, not a free latency win. Checker time must be separately compared with the existing JSON path at equal exact output/work; the card rejects a per-derivation regression.

The C1216 ABI task owns the C format tag and Datalog native/WASM host binding. C1196 can compile and test the domain-neutral decoder for wasm32, but a compile gate alone does not claim a browser-facing Datalog ABI. The C1172 guarded Lean audit runs only through its documented entry point, after reading the nested Lean guide; no direct =lean= or =lake= command is permitted.
