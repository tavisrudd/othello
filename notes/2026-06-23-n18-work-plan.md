The sequenced forward plan. Each task has concrete deliverables + acceptance. Do them in order —
the bug fix gates trusting any n=18 result; the telemetry de-risks/instruments the BuRR build.

Drive all the way to a **launched, instrumented, resumable n=18 run**:
1. **Fix any bugs** related to the migration / verdict (Phase A).

   TTY progress bar** (which roots are being searched right now + `rif`), not just in the TS file.

   **snapshotting on** (periodic, resumable) **dumping PV in the snapshots**.

So: Phase A → Phase C (incl. snapshot + PV-in-snapshot) + Phase B (incl. B5 live root display) → Launch.

## ★ Certification strategy — REVISED (2026-06-24, user) — SUPERSEDES C5/C6 + the Phase-E checker

**Full n=18 certify-from-dump is dropped — it's infeasible and ~as hard as the solve itself.**
The cert dump *is* the α-β proof DAG (the solver's memo working set), not the full reachable set
— that's why n=12 is 1.06M rows, not the 44.9M retrograde-reachable. So dumping-and-re-deriving it
is inherently ~the size of the solve. n=18 = tens of billions of rows; re-deriving them is the same
order of work as the solve (same flavour as the per-unit-cost-bound nimber-recursion levers). Certify-
from-dump never bought cheap verification at scale — it only made sense where the table fits.

**The cheaper escape: stop re-deriving the result; prove the *code* computes correct values.**
Correctness is a property of the code paths, and n=18 runs the same kernel as n≤16 plus the high-square
/ words-4–5 paths. So:

- **certify-from-dump with CPython `check_cert.py`: only up to n≤12** (already demonstrated:
  n=8 first, n=10/12 second, fault-injection rejected). The earlier "certify n=14/16 full board + a
  Rust checker" idea is dropped (CPython can't scale to 49.4M @ n=14, and the full-board dump/solve
  doesn't fit at n=16 — 9.2 B rows).
- **Then, AFTER the n=18 run, do items 1–4** (all O(sample), not O(tree)):
  1. **Primitive property tests** (where the bug class lives — the u8 bug was one truncated
     primitive): exhaustive/property checks on `d4_bits` bijectivity, `verts_of`/`att08` round-trip
     for squares 256–323, move-gen, canon, the `MAXV_POW2` mask. = the **A2** set below. Highest
     leverage per cost; domain-sized, targets the exact verdict-flipping bug class.
  2. **Differential testing vs. an independent oracle** — scale up the n=18 subposition differential
     (random legal openings → small subtrees, cross-check the fast kernel vs the slow pure-D4
     memo/`naive`). Exercises the n=18-only paths without enumerating the tree; it's how the bug
     was found.
  3. **Certify *positions* (`--after`)**, not the empty board — a real n=18 continuation has a small,
     CPython-checkable subtree; a spread of openings covers the geometry/code cheaply (demonstrated).
  4. **Sampled (probabilistic) recurrence check** on the final value table — randomly sample K
     positions, regenerate children with independent move-gen, look up their stored values, check
     `value == (∃ child LOSS ? WIN : LOSS)`. A *systematic* bug (like the u8 flip — it corrupted a
     whole class) is caught with overwhelming probability at small K. O(K), strong statistical
     confidence, never touches a TB dump.
  - (5, optional) **in-process independent re-verification pass** — after the solve, walk the BuRR
    value table in-place with from-scratch move-gen + D4 canon (no shared search/canon code). Same
    O(distinct) compute as the external checker, skips serialize + the TB write. Independence comes
    from re-implementing the rules, not from a separate process/file.

**Bottom line:** the verification burden moves from "re-derive the n=18 table" (infeasible) to "prove
the kernel computes correct values" (feasible). C5 (raw-PV-in-snapshot) is still worth keeping for
inspection/best-line, but it is **not** a proof (the bug proved a PV alone tells us nothing).

## Phase A — fix the verdict bug (BLOCKING; cheap, no 8 h rerun)

Detail + diagnosis in `handoffs/2026-06-23-n18-migration-verdict-bug.md`. The first n=18 run printed
"first player wins" with a 14-move (even) terminal PV → violates the codebase's own
`first_wins ⟺ odd-PV` contract (`mod.rs:302`). Likely a **loss→win flip** in the n=18-only paths
(words 4–5 / squares >255 / `MAXV_POW2`) — never oracle-tested (n≤16 don't touch them).

- **A1. Runtime PV-parity guard.** In the `solve` command path (not just the n≤8 test), after
  computing `first_wins` and the PV: `assert/loud-warn first_wins == (pv.len() % 2 == 1)`. Acceptance:
  re-running the buggy n=18 (even a shallow probe) trips the guard instead of printing a wrong verdict.
- **A2. Three targeted unit tests** (find the flip without a long run):
  - `d4_bits` is a **strict bijection** on random 6-word `Bits` — no two distinct inputs map equal
    (the high-word-fold must not alias; words 4–5 only ever set at n=18).
  - `verts_of`/`att08` round-trip for **squares 256–323** (u16, no `as u8` truncation survived).
  - `MAXV_POW2` mask is a **no-op** for all degrees `0..=324` (`d & (MAXV_POW2-1) == d`), and the
    counting-sort `count`/`degbuf` arrays are sized `MAXV_POW2`.
  Acceptance: one fails → the bug; fix → all green.
- **A3. Shallow n=18 re-check** after the fix (depth-cap or `QUEENS_FAST=0` probe), confirm the guard
  is happy and the verdict is self-consistent. Acceptance: parity holds; verdict likely flips to
  **second player** (the even-n streak). Decide then whether the full (all-roots-losing) n=18 sweep
  is worth the compute.

## Phase B — telemetry & tooling (instrument before the big build)

These make the BuRR build measurable and would have caught the issues this run hit. All low/zero
overhead; specs already stubbed in `n18-migration-changemap.md` (TS section).

- **B1. Live TT hit-rate in `QUEENS_TS_FILE`.** Expose a running `(gets, hits)` pair from the solver
  (per-worker probe counters already exist under telem/M_COLD); the watcher samples + emits
  `"gets":N,"hits":M` per JSON tick ⇒ **hit-rate over time = Δhits/Δgets**, no `--distinct`/HLL,
  ~zero overhead. Optional: per-pc bands for the cold-fraction *curve*. (This run was lean, so we only
  got the end-of-run M_COLD aggregate; a live curve shows the DRAM-latency entry directly.)
- **B2. In-flight root count `rif` in `QUEENS_TS_FILE`.** Atomic inc on root-enter / dec on root-exit
  (`QUEENS_ROOT_TIMING` already stamps those); watcher emits `"rif":K`. Exposes the parallelism
  *shape* (`rif≈1` + nested = giant-root tail; `rif≈24` = balanced). This run we had to *infer* the
  single-root shape from worker-count dips.
- **B3. Root-timing reporting fix.** Distinguish **`WIN_PROVED(sq)`** / **`SKIPPED`** (winning root
  found ⇒ existential stop) / **`LOSS_PROVED`** from "ran in 0.0s". The current table implies 44 roots
  finished instantly; they were *never searched* (the `0/45` mystery). Acceptance: the n=18 table
  reads `WIN_PROVED(I9) · SKIPPED×44 · LOSS_PROVED:none` (once the verdict bug is fixed, the labels
  will be correct).
- **B4. `count --by-ply`** — per-ply (≈ per-pc, monotone) **distinct** distribution on n=14/16. Needed
  to size the BuRR build: the value-only ply-windowed freeze needs each ply's frontier resident in RAM
  *before* freeze. Acceptance: a per-ply distinct histogram → identifies the **widest ply** → confirms
  it fits RAM (or flags that the deep plies need external-memory DDD).
- **B5. Live in-flight root display in the TTY progress bar.** Beyond `rif` in the TS file, show in
  the **live bar which roots are currently being searched** (e.g. `searching: I9(sq152) [+3 nested]`,
  or a compact `rif=K · {sq…}`). Same root-enter/exit stamps as `rif`/`ROOT_TIMING`; cold (no per-node
  cost). Acceptance: during a run the bar shows the live root set — this run we could only *infer*
  "one giant root I9" after the fact. Pairs with the B3 reporting fix.

## Phase C — BuRR-backed iso-dense (Phase 3b) + snapshotting

Full architecture in `2026-06-23-burr-backed-iso-dense-design.md`. **Decisions locked:** Path B
(value-only ply-windowed, ~1.1 bit/key, ~7–12 GB) — the *only* mode that fits n=18; membership-
carrying (`fp=44`, ~62 bit/key, ~300 GB) is dead as a fix. The **gate is cleared** (the run's M_COLD
confirms the memory-bind / re-expansion). It's a **search restructure** (DFS → ply-batched
breadth-first + explicit DDD + per-ply value-only freeze), keeping the dense getK layer.

**Allocation (user, 2026-06-23):** BuRR archive = **14 GB nominal, up to 17 GB if needed** (matches the
iso-burr n=16 precedent `QUEENS_BURR_CAP_GB=14`; 17 GB = the old flat-TT n=16 size, the safe ceiling on
this 26 GB box — iso-burr plateaued at 17.5 GB RSS). Comfortable for the ~7–12 GB value-only estimate
(14 GB @ ~1.1 bit/key ≈ ~100 B keys). Use **huge pages** for the archive backing — reuse the flat-TT
machinery (`zeroed_huge_atomics` = `MADV_HUGEPAGE` + the `QUEENS_TT_COLLAPSE`=`MADV_COLLAPSE` for ≥4 GB);
the ribbon archive is randomly accessed, so 4 KB pages would TLB-thrash exactly like the TT did.
**Caveat:** 14–17 GB is the *archive* budget — the **per-ply frontier buffer** (current ply expanded
*before* freeze) is **separate** and must fit the remaining ~9–12 GB; B4 (`count --by-ply`) confirms the
widest ply fits, else C3 external-memory spill. So watch archive(≤17) + frontier ≤ ~24 GB usable.

- **C1. Wire + unit-test `ply_store.rs`.** Add `mod ply_store;`, compile, fix the inevitable
  API/visibility errors, unit-test `PlyWindowStore`: build→get round-trip on a synthetic ply, and the
  value-only **collision rate** (64-bit key, no fingerprint — confirm ~2⁻⁶⁴/pair as designed).
- **C2. In-RAM ply-windowed driver** (`iso-dense-ply`), for the case every ply fits RAM (validate
  n≤16 first). Replace the DFS in `wins_inc` with: per ply (deep→shallow) expand frontier → resolve
  children via getK or the already-frozen deeper plies → DDD → freeze value-only → next ply.
  Acceptance: **exact gates hold** — n=12 distinct = 1,060,823, lineage, n=14 ≈ distinct / re-exp ~1.0×.
- **C3. External-memory DDD** for the widest plies *only if* B4 shows they exceed RAM (sort-based
  spill, classic frontier search). Then the real n=18 (likely the second-player all-roots sweep).
- **C4. Snapshotting / resume (REQUIRED — the flat-TT iso-dense could NOT do this; `tt()` is `None`).**
  The value-only per-ply segments are immutable ⇒ the **natural checkpoint**: persist each frozen
  ply's `ShardedArchive` to disk (reuse `burr.rs`'s archive serialize/deserialize), plus the driver's
  resume cursor (which plies are frozen, current frontier). **Resume** reloads frozen plies and
  continues. Periodic + on-signal (mirror the existing `--checkpoint`/SIGUSR2/`S` keypress UX).
  Acceptance: kill mid-run, resume, finish with the same verdict; an n=18 multi-hour/day run is no
  longer all-or-nothing. (The flat-TT n=18 run was 8 h all-or-nothing; a second-player sweep could be
  days — snapshotting is essential.)
- **C5. Dump the RAW PV-trace data in the snapshots (not just the final report).** Capture the
  principal-variation/best-line trace **as it is built during search** (the incremental per-root proof
  line / the live PV the search maintains) and write it into each snapshot — not the post-hoc
  `principal_variation()` reconstruction. So a resumed or inspected snapshot carries the in-progress
  optimal-line evidence. Acceptance: a snapshot taken mid-search contains the raw PV-trace state, and
  reloading it reproduces the same line the live search was on.
- **C6. Certification dump — enough data to INDEPENDENTLY validate the verdict.** ⚠ **SUPERSEDED for
  n=18 — see the "Certification strategy — REVISED" block above** (full-board certify-from-dump is
  dropped as infeasible; CPython checker only to n≤12; the n=18 confidence plan = items 1–4 after the
  run). Kept below for the n≤12 history. Motivated
  directly by the verdict bug: the solver's own verdict can't be trusted, and **the PV alone is NOT a
  proof** (one line told us nothing — it even contradicted the verdict). The run must dump a
  **certificate** that a *separate, simple program* (game rules only — move-gen + terminal test, no
  solver code) can check, so a bug in the search/canon/verdict logic cannot fool it. Two sound forms:
  - **(A) Winner's strategy subtree** — winner-nodes: the chosen move; **loser-nodes: ALL legal
    moves**; leaves: terminal + correct parity. Self-contained classic proof tree. Checkable, large.
  - **(B) Value table + O(distinct) recurrence check — the BuRR-snapshot fit.** The value-only per-ply
    archives ARE the value table; an independent checker walks positions deep→shallow, regenerates
    children, looks up their values, verifies `value == (∃ child LOSS ? WIN : LOSS)`, terminals =
    LOSS-for-mover, root → verdict. **Would have caught the I9 flip.**
  - **Subtleties (where a *fake* certificate sneaks in):** (1) **collision-safety** — value-only
    `fp=0` 64-bit keys give ~tens of hash collisions at ~50 B positions (fine for solving, NOT for
    certifying) ⇒ the certificate needs wider keys / a fingerprint / a recheck pass; (2) **loser-node
    completeness** — the checker must confirm *all* legal moves are covered (a missing refutation is
    how a false win passes); (3) **independent move-gen** — the checker reimplements the rules, does
    not import solver canon/`d4_bits`; (4) **terminal + parity** — verify each leaf is truly terminal
    and `winner makes the last move` (the invariant this run violated).
  - **Deliverable:** the snapshots constitute a checkable certificate (collision-safe value table +
    the strategy/PV witness) **+ a tiny independent checker** (separate codebase, e.g. Python) that
    re-derives the verdict in O(distinct). Acceptance: the checker certifies n≤16 (matches the known
    verdicts) and then the n=18 result — **a result we don't certify, we don't claim.**

## Phase E — Launch the instrumented, snapshotting n=18 run

Once A–C land: **start the run in a tmux pane** (`queens` session, bare on the TTY so the live bar +

**plus snapshotting on** (periodic, resumable) **dumping the raw PV trace** (C5) **and the certification
data** (C6) in each snapshot — so any verdict the run produces is **independently checkable**, not
taken on the solver's word. Use a **real disk** path for the TS file + snapshots (not `/tmp` =
tmpfs/RAM). Box hygiene + GPU-quiet (monitor off / lock) per the first run. **Then verify the verdict
per the "Certification strategy — REVISED" block** — NOT a full certify-from-dump (infeasible at n=18),
but the items 1–4 confidence plan (primitive property tests + subposition differentials + `--after`
position certs + a sampled recurrence check / in-process re-verification pass). **A verdict we can't
back with that evidence, we don't claim.** This is the end-to-end goal.

## Phase D — cluster scale-out (future, n≥20)

Detail in the BuRR design doc's cluster section. **TDS** (hash-partition positions, route-work-to-
data) kills the giant-root tail; **gossip BuRR segments for k=2 fault-tolerance, not full
replication**. On **2.5 GbE**: viable *iff batched* (per-node demand ≈ (total msgs × bytes)/(single-
box wall) ≈ ~95–190 MB/s batched / jumbo frames vs ~390 MB/s unbatched; demand ~constant in N). Few
fat nodes > many thin. **Derisk first:** instrument an n=14/16 run for the cross-node edge count +
payload size, and microbenchmark the actual 2.5 GbE at the target pps before building anything.

## Sequencing & rationale
A (bug) is **blocking** — no n=18 result is trustworthy until the parity guard is green. B (telemetry)
is cheap and makes C measurable + would have caught this run's issues — do it next. C (BuRR) is the
multi-session payoff that makes n=18 actually fit + bounded. D (cluster) is only for n≥20 or for
crushing the n=18 giant-root wall in wall-clock once the single-box version works.
