# C864 — classification of the generated modules finitegeom carries

**Lane:** `build-sys` · **Date:** 2026-08-05

**Verdict: finitegeom carries one generated module, not three.  `SplitQuadraticPinching` and
`AMELU/FourCopyContraction` are hand-written semantic source that the detection rule mistook for
generated payload, because it matched ordinary prose about an ideal generated by `a`.  The one real
finding, `ClebschArithmeticGluingData`, is a frozen finite table of 20 KB carrying seven
definitions and no generated proof; the determination is that it is human-scale semantic source and
stays, declared in a new permanent `resident_family` table rather than left unclassified.  The
detection rule is tightened in both the boundary checker and the portfolio audit, and the checker
now reads whole files, which is what a delimited generated block below a module's preamble
requires.**

## The three modules

The portfolio audit (`notes/2026-08-05-c864-certificate-portfolio-audit.md`) reported three
generated modules byte-identical across the monorepo, the `finitegeom` base and the golden quantum
statistics export, and correctly raised their priority on the grounds that finitegeom multiplies them
across every paper export.  Reading them settles two of the three the other way.

| module | banner match | disposition |
|---|---|---|
| `RelativeConicArcs/SplitQuadraticPinching.lean` | line 24, `the principal ideal generated by \`a\`` | false positive; hand-written semantic source |
| `RelativeConicArcs/AMELU/FourCopyContraction.lean` | line 72, `words generated by \`G\`` | false positive; hand-written semantic source |
| `RelativeConicArcs/ClebschArithmeticGluingData.lean` | line 429, `Generated by \`verification/clebsch_arithmetic_gluing/generate.py\`` | genuinely generated data; determined human-scale, stays |

Neither false positive names a generator, has a do-not-edit marker, or carries a generated block.
Both matched because the rule accepted `generated by` followed by anything in backticks, and Lean
mathematics says that about subgroups, ideals, and codewords constantly.  The boundary checker's own
comment already named this risk; the regex did not enforce what the comment described.

## The one real finding

`ClebschArithmeticGluingData.lean` is 1,387 lines in two parts.  Lines 1--427 are hand-written: 17
theorems checking the tables by `decide`, over the two coordinate reductions of the `A3`, `B3` and
`H3` vertex sets, the matchings, the sheet exchanges and the split Coxeter-square multipliers at
`q = 5, 7, 11`.  Lines 428--1384 are a block delimited by `BEGIN`/`END ARITHMETIC GLUING
CERTIFICATE DATA`: 20,166 bytes, seven `def`s of literal lists, no theorem, no `decide`, emitted by
the tracked generator `lean/verification/clebsch_arithmetic_gluing/generate.py` with its
`certificate.json`, `manifest.sha256`, `replay.py` and `source_data.json` alongside it.  Its
consumers are four hand-written modules in the same area: `ClebschArithmeticGluing`,
`ClebschA3InvariantMatching`, `ClebschB3InvariantMatchings`, `ClebschH3InvariantMatchings`.

That shape is not the externalization case.  The families that earned their own packages are
exhaustive proof closures — the order-16 package seals 1,331 modules, the order-eleven point-orbit
family 60 generated row leaves each carrying its own per-row action theorem.  This is a finite input
table a reader can read, whose every mathematical claim is proved by hand-written Lean beside it.
The acceptance criteria admit exactly this outcome: a written determination that a family is
human-scale semantic source and not an externalization candidate.  Manufacturing an official package
for 20 KB would also contradict the contract's ban on an umbrella package, since no existing package
covers the Clebsch rank-three area.

`ClebschSchemeFourierData.lean` gets the same determination on the same grounds — 13 KB, nine `def`s,
no proof, generator and digest-checked replay under `lean/verification/clebsch_scheme_fourier/`, one
consumer.  It is not in finitegeom, so it was never part of the propagation finding, but it sat in the
same unclassified entry and there is no reason to decide it separately.

## What changed

- `lean/scripts/lean-certificate-boundary.py` and `lean/scripts/lean-certificate-portfolio-audit.py`
  now require the backticked name after `generated by` to look like one, by containing a path
  separator or an extension dot.  Measured over every tracked Lean source: 9,407 files matched
  before, 9,405 after, and the two dropped files are exactly the two false positives above.
- The boundary checker reads whole files instead of a 4,096-byte head window.  The arithmetic-gluing
  banner sits at byte 19,904, so the checker had never seen it; only the full-file portfolio sweep
  had.  The real-tree check takes about two seconds either way.
- `lean/scripts/test_lean_certificate_boundary.py` carries both real false-positive sentences as a
  fixture.  The suite is green at 14 tests; the fixture fails against the old regex.
- `lean/trust/certificate-packages.toml` loses its `resident-unclassified` entry and gains a
  permanent `[[resident_family]]` table declaring the two frozen tables, each entry naming the
  determination that admits it.  The checker treats resident families as declared.  `pending_family`
  now holds only `external-pending` families, so its emptiness once again measures exactly the
  remaining externalization scope, as acceptance criterion 9 requires.
- Both real-tree checks pass, with and without `--verify-official-libraries`.  The portfolio audit
  now reports one generated file in finitegeom and one in the golden export, byte-identical
  (sha256 `2ca60d94d0bab623…`), where it previously reported three in each.

## Replay

```sh
python3 lean/scripts/test_lean_certificate_boundary.py
python3 lean/scripts/lean-certificate-boundary.py
python3 lean/scripts/lean-certificate-boundary.py --verify-official-libraries
python3 lean/scripts/lean-certificate-portfolio-audit.py ~/src/lean/finitegeom \
  ~/src/lean/finitegeom-golden-quantum-statistics
```

No Lean, no lock, no build window; all four commands read file contents only.

## Left open

The arithmetic-gluing banner names `verification/clebsch_arithmetic_gluing/generate.py`, a path that
exists in this repository and in neither finitegeom nor the golden export that carry the module.  That
is the same defect class the order-25 package fixed by repathing its banners, and the repair is a
banner edit with no mathematical content.  It is not done here because editing a base-carried source
requires the finitegeom re-export, which is already deferred to the single atomic window that also carries
the orientation rename and the order-eleven package re-seal.  Queued for that window, alongside the
same check for `ClebschSchemeFourierData`, whose banner names `lean/verification/...` from a module
that ships without it.
