## Verdict

**Every recorded value in the report re-derives, and one code defect and one wrong result were
found.** All 2,543 ratio, interval, A/A null, per-arm mean, peak-resident-set and provenance values
across the twelve `ab.py` receipts recompute **bit for bit** from their raw `.jsonl` sidecars; every
Soufflé wall ratio, interval, instruction median, resident set and phase figure reproduces exactly,
and my own independent recomputation of the geometric means and t-intervals from the raw samples
agrees to every printed digit; every frontend and backend stage ratio, cycle ratio, resident set and
closure digest reproduces once the aggregation is identified as the `byte` variant; my own replay of
the reach table reproduces all fifteen rows' derived counts and reserved-byte figures exactly and
their resident sets to within 0.1 per cent, including both `Budget` refusals; three of the four
C1191 boundary cohorts reproduce their largest dictionary, their resident set to within 0.03 per
cent, and their first refusal's budget name, found value and limit exactly; and the cold-start
stage reproduces to the digit, including 112,918 / 225,833 / 451,667 own minor faults, 11,291.7
faults per iteration at every repeat count, and the constant 4,461-to-4,466 offset between `perf`
and `/proc/self/stat`. Both deliberate mutations fail by name in milliseconds with exactly the
messages the report quotes, and mutation A reproduces the described asymmetry: it passes all three
`workspace_commit` integration tests and hangs `allocation.rs`. Core `cargo test --all-features`,
clippy and `cargo fmt --check` are green at `2be1e68` with **81 test binaries and zero failures**,
the count the report states.

The **code defect** is that `Demand::shape()` does not check the program's domain while the
high-water reset recomputes every row's key with the current plan's domain, so a workspace handed
between two same-shape programs over different domains is cleared with the wrong key function. On
pristine shipped code this makes `evaluate_into` **not terminate**: a probe that evaluates a chain
closure over domain 4,096, then a matching closure over domain 2,048 of identical shape, then the
first program again into the same workspace hangs on the third call, past a 180-second cap, with
`shape()` raising no `Error::Source`. Before C1198 the reset was a `fill(NONE)` over the capacity
and was domain-independent, so this is a gap the task opened. The suite's own
`a_reused_workspace_agrees_with_a_fresh_one_under_every_policy` establishes that cross-program
workspace reuse is an intended, tested capability; it varies the fact set and never the domain.

The **wrong result** is that the cache-line stagger is credited with repairing the 9 per cent cycle
regression and it does not. The regression itself reproduces cleanly — control `b7921a0` against the
pre-stagger arm `356fce6` gives cycles 1.087 [1.070, 1.105] and 1.092 [1.081, 1.103] with A/A nulls
of 1.008 and 0.997 — but so does its absence on a binary with **no stagger at all**: the report's own
`c1198-nostagger-probe`, built from the `6078142` tree with the stagger multiplied out, runs at
0.994 and 0.993 against the same control. The stagger's isolated effect is 0.996 [0.978, 1.014] and
0.996 [0.984, 1.008], both intervals containing unity, against the report's quoted "30 per cent off
the cycles" — a point estimate whose own recorded 95 per cent interval is [0.268, 1.815] and
therefore contains unity, which the report does not print. What repairs the regression is the rest
of the `356fce6`-to-`6078142` delta, and the only other thing in it is the private `--cold` driver
edit: `Demand::evaluate_into` is 7,741 instructions at `356fce6` and 7,701 at both the no-stagger
probe and `6078142`, with the bodies differing in thousands of lines. That is the same ThinLTO
effect the report's mystery ledger item 3 correctly identifies and measures at 0.8 per cent of
instructions — it is also worth 9 per cent of cycles, and the report gives that credit to the wrong
change. Recorded deviation 1's "without it the change is a memory win and a wall-time loss on the
dense cohorts, so it is not optional" is refuted by measurement.

Beyond those, seven record defects: the page-fault profile's candidate row was taken on `356fce6`
and is labelled `6078142`; the replay block's two `perf` loops name an arm (`ed99963`) that neither
profile on disk was taken on; the cache A/B and the stagger probe are described as "on the shipped
arm" and are on `6078142`; recorded deviation 7 still says the fill boundary is thirty-two bytes per
row after the repair set it to sixty-four; and three small numeric slips. Two gates that the report
treats as load bearing turn out not to bind what they are for: **inverting the fill-versus-walk rule
passes every one of the fifteen `ergodis-rules` test binaries**, and **dropping the stagger offset
from `Drop`, which leaks 51 GiB of address space over 200 reservations, passes them too**.

## Defects found

**1. The cache-line stagger is credited with repairing the 9 per cent cycle regression and it does
not repair it. Major; wrong result.** Location: recorded deviation 1 ("Without it the change is a
memory win and a wall-time loss on the dense cohorts, so it is not optional"), disposition item 3
("30 per cent off the cycles of `closure` dense at N = 256, and it is what makes the change a
wall-time win rather than a wall-time loss on the dense cohorts"), mystery ledger item 2
("*Nothing about this item is open*"), and the vibe check's "a rotating cache-line stagger fixes it
at exactly zero instruction cost".

The regression is real and reproduces. Control `closure_ballpark-b7921a0` against the pre-stagger
arm `closure_ballpark-356fce6`, five rounds, CPU 5, box load 0.45 to 0.75:

| Cohort | instructions | cycles | 95 per cent interval | cycle A/A null |
| --- | ---: | ---: | --- | ---: |
| `closure` dense 256 | 0.99161 | **1.08716** | [1.07009, 1.10450] | 1.0078 |
| `closure` dense 512 | 0.99160 | **1.09217** | [1.08107, 1.10339] | 0.9971 |

So is its absence on a binary that has **no stagger**. The report's own
`~/.cache/ergodis/bin/c1198-nostagger-probe` is the `6078142` tree with the stagger multiplied out;
against the same control, five rounds, load 1.15 to 1.22:

| Cohort | instructions | cycles | 95 per cent interval | cycle A/A null |
| --- | ---: | ---: | --- | ---: |
| `closure` dense 256 | 0.98335 | **0.99361** | [0.96881, 1.01904] | 0.9803 |
| `closure` dense 512 | 0.98327 | **0.99284** | [0.97676, 1.00919] | 1.0009 |

And the stagger's own isolated effect, the report's exact probe pair rerun at four rounds on a quiet
box (load 0.47 to 0.69), is nothing: `closure` dense 256 at 0.99586 [0.97827, 1.01378] with a null
of 0.99299, and dense 512 at 0.99606 [0.98410, 1.00816] with a null of 0.99967. Both intervals
contain unity. The report's quoted 0.6972 is faithfully recorded — my re-derivation reproduces it
bit for bit from the sidecar — but **its own 95 per cent interval is [0.26776, 1.81528]**, which the
report does not print while calling the point estimate "30 per cent off the cycles ... with a cycle
null of 0.9915". An A/A null bounds the noise between two adjacent measurements; it does not license
a point estimate whose paired interval spans a factor of seven. The report itself declines to read
the companion dense-512 row because its null is 0.8456, so the stagger probe supplies no readable
cycle evidence on either dense cohort.

What does repair the regression is the rest of the `356fce6`-to-`6078142` delta, and the only other
thing in it is the private `--cold` driver edit `b5f10e7`. The kernel's compiled body confirms it:
`Demand::evaluate_into` is **7,741 instructions at `356fce6` and 7,701 at both the no-stagger probe
and `6078142`**, and diffing the two bodies with branch targets and immediates normalized leaves
thousands of differing lines — a wholesale recompilation, not a constant. That is the same ThinLTO
effect the report's mystery ledger item 3 identifies and measures at 0.8 per cent of instructions;
it is also worth about 9 per cent of cycles, and the report gives that credit to the stagger.

Two things this does **not** say. It does not say the stagger is harmful: it costs exactly zero
instructions, at most 4,032 bytes of address space per table, and its measured cycle effect is
0.4 per cent favourable with intervals containing unity. And it does not say the 4 KiB-aliasing
mechanism is wrong about the *pre-stagger* arm; it says the mechanism was never isolated, because
the binary the report calls unstaggered already carries the repair. *Repair*: rewrite recorded
deviation 1, disposition item 3, mystery ledger item 2 and the vibe-check paragraph around the four
measurements above; reopen item 2 with its evidence gap stated as "the regression's cause is not
isolated, because the arm that lacks the stagger also lacks the driver edit"; and either retain a
probe of the `356fce6` tree with the stagger added, which is the isolation that was needed, or say
the mechanism is unestablished.

**2. A store-to-load-forward counter contradicts nothing and supports nothing, and it was never
run. Minor; missing measurement for a settled claim.** Mystery ledger item 2 names the load-store
unit and a false dependency as the mechanism and says "the counter that would show it is not in the
playbook's supplementary set". It is on this PMU: `ls_bad_status2.stli_other` (store-to-load-forward
conflicts) and `ls_stlf` (successful forwards), both AMD Zen core events, both at 100.00 per cent
enabled. On the report's own probe pair they move by nothing: conflicts at 1.2974 with an A/A null
of 1.6215 on `closure` dense 256 — unreadable — and 1.0082 with a null of 1.0284 on dense 512, on
absolute counts of 123 K and 1.5 M per evaluation against 68 M and 529 M cycles, far too small to
buy a tenth of the loop; `ls_stlf` is unity to three parts in ten thousand on both. Given defect 1
this measures the wrong pair, so it settles nothing either way; it belongs in the record because the
report asserts the counter does not exist. *Repair*: name the two events, and run them on whichever
pair does isolate the stagger.

post-stagger one. Moderate; record.** Location: the "Page faults, by symbol, before and after"
table, whose candidate row reads "candidate `closure_ballpark-6078142`". The file that produces
those exact percentages is `~/.cache/ergodis/perf-c1198/cycle-faults-candidate.data`, whose `perf`
header records the command as `closure_ballpark-356fce6`. Every printed figure is faithful to that
file — 53.16, 18.99, 7.59, 5.06, 3.80, 2.53, 1.27, 1.27, 1.27, 1.27 — and the 15,733-fault total is
that run's. The control row is correct: `cycle-faults.data` was taken on `b7921a0`. The conclusion
is unaffected, because `356fce6` already carries all three deliverables and the profile is about
where the faults come from; the arm attribution is simply wrong. The same row is also an incomplete
listing of what it claims: at the one-per-cent cut the profile has twelve symbols, and the report

C1199 step 2 done: 19

### F. Reasoning

**Item 2, 4 KiB aliasing as the mechanism for the 9 per cent cycle regression.** *The evidence given
does not support it, and the reason is not the mechanism but the isolation.* The isolating A/B
compares `c1198-nostagger-probe` against `closure_ballpark-6078142`, and the probe is built from the
`6078142` tree, which already carries the driver edit that removes the regression. Measured against
the C1192 control, the probe shows no regression at all: 0.994 and 0.993 in cycles with nulls of
0.980 and 1.001. So the comparison the report calls "a probe build differing in that one expression"
is a comparison between two binaries that are both already repaired, and its 0.6972 has a 95 per
cent interval of [0.268, 1.815]. *What it does not exclude*: essentially everything — any
page-offset-sensitive effect, any L1 set or bank conflict, and, as the measurement now shows, the
whole-body recompilation the driver edit causes. *The one measurement that would settle it*: retain
a probe built from the **`356fce6`** tree with the stagger added, which differs from `356fce6` in
exactly that one expression, and run it against `356fce6` with `ls_bad_status2.stli_other` and
`ls_stlf` beside cycles. If the stagger is the repair, that pair shows it; if the driver edit is,
that pair shows nothing and the pair `356fce6` against `c1198-nostagger-probe` shows everything.

**Item 3, ThinLTO attribution of the 0.8 per cent.** *The evidence supports the conclusion, and the
conclusion is stronger than the report claims.* The elimination is complete: the core difference
between `356fce6` and `6078142` is exactly `271d648`, the stagger, and the private difference is
exactly `b5f10e7`, the `--cold` mode; the stagger probe shows 1.00000 instruction change to five
decimals on four cohorts; so the 0.7 per cent belongs to the driver edit. My re-runs confirm both
endpoints independently, at 0.99161 and 0.98335 against the same control. *What it does not
exclude*: the named mechanism. "Through ThinLTO's module summary" is an inference from the C1170
precedent, not a measurement — the same instruction delta would follow from any change in inlining,
codegen-unit partitioning or register allocation in a shared unit. *The measurement that settles the
larger claim*, which I ran: `Demand::evaluate_into` is **7,741 instructions at `356fce6` and 7,701
at both the no-stagger probe and `6078142`**, with the bodies differing in thousands of lines after
normalizing branch targets and immediates. An untimed driver mode did not shift a counter; it caused
the kernel to be recompiled. That is worth stating in the report far more strongly than 0.8 per
cent of instructions, because the same edit is worth 9 per cent of cycles — see defect 1.

**Item 8, locality at N = 65,536.** *The evidence supports the structural half and not the
mechanism, which is what the report already says by marking the item open.* The structural half is
better supported than the report shows: the receipts' own addressing blocks put both join indexes
at 65,536 direct slots under **both** bounds, so the membership table at 16,777,216 against
2,097,152 slots really is the only structure whose shape changes, and there is no index confound.
Commit is excluded by arithmetic the report does not do: 19,304 KiB of extra peak resident set is
4,826 pages, 3.5 ms at C1170's 734 ns per faulted page, against a 373 ms residual. *What it does not
exclude, and what now runs against it*: the miss story. The playbook's supplementary cache set on
that cohort under the two bounds, same binary, same output digest, nulls inside one per cent, puts
the **sized** bound — the faster one — at 1.32 times the default bound's cache references, 1.52
times its cache misses and 1.37 times its L1 load misses per evaluation. The caveat is that
`--evaluate-only` measures a warm repeated loop and the 216 ms residual is one cold evaluation, so
this is not a refutation; it is the removal of the intuition the explanation rested on. *The one
measurement that would settle it*: the report names it correctly — the same cohort with the
membership table's slot count varied independently of the row bound, with cache and TLB counters —
and that still needs a selector the evaluator does not have. A cheaper intermediate, available
today, is the cold single-evaluation regime instrumented directly: `perf stat` the `--process` arm
under both bounds with the cache set, which attributes the 216 ms rather than the steady-state loop.
