* Scope and verdict

This is a private architectural review of Ergodis as it exists on 2026-09-22,
including the core, private library, task binaries, extension packages, browser
and native hosts, Python interface, evidence/export pipeline, and developer
tooling. It documents implementation, not a proposed replacement architecture.
The final sections give prioritized changes and a navigable module inventory.

Ergodis has a coherent central design: compile a finite problem into specialized
immutable data; allocate mutable worker storage explicitly; execute bounded,
usually allocation-free kernels; reconstruct witnesses; admit claims through
checkers with explicitly limited authority. The recent contract/checker split
strengthens that design. Several good boundaries are enforced by dependencies
and tests, rather than only by convention.

The main architectural debt is uneven enforcement of those boundaries. A large
flat core and private library contain both mature reusable kernels and research
families; multiple workflow/control systems coexist; some promoted algorithms
still have private implementations; validated-state guarantees vary considerably
between APIs. The relational execution path is substantially implemented, but
the complete transferable proof chain from Rel source to final answer is still
unfinished. Two Datalog certificate formats are not two independent completeness
implementations.

*Portability is not established by WASM support.* There is a concrete macOS
compile blocker in the rules crate, Windows has missing native host capabilities,
and the current locked canonical WASM check fails before compilation. ARM has a
promising portable computational base and guarded x86 specializations, but there
is no native ARM validation from this review. Portability needs a matrix of
components, features, targets, and resource behavior.

** Technical due-diligence grade

*Overall: B−. Confidence: moderate.* Ergodis contains substantial engineering
with a coherent central design, but product maturity is uneven. This is an
engineering-readiness assessment of the reviewed revisions. It weighs the
implementation, maintained boundaries, and demonstrated validation; it is not
an arithmetic average of the category grades.

| Area | Grade | Basis in this review |
|------+-------+----------------------|
| Technical substance | A− | Serious specialized kernels, explicit performance discipline, meaningful verification machinery |
| Architecture | B+ | Strong plan/workspace separation and inward dependencies; several competing workflow surfaces (F08–F10) |
| Correctness assurance | B | Scoped checks and independent fixtures; shared completeness logic and incomplete Rel evidence chain (F04–F06/F15) |
| Maintainability | C+ | Large public surfaces, duplicated implementations, inconsistent validated-state APIs, documentation drift (F06–F08/F16–F17) |
| Portability/release readiness | C− | Concrete macOS blocker, Windows host gaps, stale WASM lock, and insufficient native target validation (F01–F03/F11/F13–F14) |

The diligence recommendation is to continue development with a focused hardening
phase before positioning Ergodis as a broadly portable platform. Most findings
call for consolidation and stronger enforcement of existing boundaries. The
largest uncertainty is whether new features can be maintained consistently
across execution, verification, and host paths without multiplying exceptions.

Confidence is moderate because this review combines source inspection with
scoped tests. It does not establish whole-system correctness or production
reliability. The technical-substance grade recognizes implemented engineering;
it does not certify every algorithm or imply a novelty assessment.

The remediation plan below prioritizes inexpensive, independently reviewable
steps. Closing the build blockers would improve release readiness, but an A-level
assessment would additionally require stronger evidence independence, demonstrated
native platform coverage, and sustained control of the API/maintenance surface.

** Method and limits

The review inventories all declared workspace crates and top-level library
modules, examines component manifests and contracts, and traces representative
paths through compilation, execution, verification, persistence, and provider
loading. It reads implementations at the boundaries implicated by findings.
It is an architectural source review, not a line-by-line audit of every solver,
a mathematical soundness proof, or a complete hostile-input security audit.

Measured source size, including comments and inline tests: core =src/= has 113
Rust files / 108,043 lines; core =crates/= has 81 Rust files / 27,950 lines;
private =src/= has 226 Rust files / 166,630 lines; private =tasks/= has 145 Rust
files / 44,519 lines. The core facade declares 75 public modules and the private
facade 192. These counts describe tracked source, not production-only code.
Provider packages share additional source by path; summing package sizes is not
a count of independent implementations.

The selected source/configuration paths were clean at review start. No engine
source was changed. Validation and its limits are recorded below. The initial
handoff read exceeded the command-output budget; it was replaced by bounded
reads. No conclusion relies on its truncated output.

Core must not depend on private adapters. Private providers may compile selected
private modules against the public core and expose opaque native/WASM packages.
Evidence is authored in core and copied one way to the evidence repository;
developer tooling and private reports do not ship. This is a real publication
boundary, distinct from Rust =pub= visibility.

The export script filters the tracked tree, rewrites evidence references,
regenerates the content manifest, runs publication lint, and creates a snapshot
commit. The evidence refresh deliberately does not delete absent files, so
removals need explicit synchronization. The current =.publicignore= has an empty
work-in-progress hold section: new source is eligible by default unless excluded.
The export policy therefore depends on review and lint as well as placement.

useful and should survive cleanup.

** Private subsystems and extension packages

The private root library has several recognizable clusters: Hadamard/quotient
research and specialized finite searches; causal and leakage models; detector,
matching and predecoder machinery; retained composition and semantic plans;
allocation/LRC/resource adapters; representation discovery; and the Rel compiler.
The =g41_*=, =g53_*=, =q18_*=, =q29_*= and similar families remain strongly
workload-specific even though they are exported from the reusable private tier.

=OpenProblem= is an existing, deliberately small abstraction for retained
composition: a compiled context, summary type, identity, composition, and value
readout. Normalization, tensoring, and reconstruction are separate capabilities.
=RetainedTree= and the matrix/function/monoid/semiring adapters are real private
implementations, not a missing framework to invent. They do not define a
universal executor or every solver's lifecycle.

The LRC model/plan/query adapter provides a particularly clear ownership model:
=RepairModel= owns source capacities, =RepairPlan= retains compiled transfer data,
and an admitted =BudgetQuery= borrows its plan. A query cannot accidentally be
used against another plan through that API. Some other interfaces are weaker.

The private workspace contains eight family providers plus a component adapter:
=lrc=, =qec=, =scheduling=, =hadamard=, =css=, =composition=,
=parameterization=, =fault=, and =component-provider=. Seven family manifests
compile the shared =packages/execution-provider/src/lib.rs= with a family
feature. Parameterization has its own implementation; the component adapter
wraps LRC through WIT. =execution-provider= itself is shared source, not an
independent Cargo package.

The shared provider uses =#[path]= to compile selected private source files
directly. This avoids a dependency on the entire private library and its Unix
control feature, permits separate payloads, and reuses the actual kernels.
It also duplicates module wiring, feature lists, and build context. Provider
families are mutually exclusive within each package's shared entry source.

* Execution and evidence paths

** Prepared plans, hot state, and witnesses

The common pattern is cold structural validation and representation selection,
then owned worker storage, then a typed inner kernel. Range-sized IDs, contiguous
pools, explicit record layouts, iterative traversal, monomorphized modes, and
allocation-count regressions are recurring mechanisms. Immutable plans can be
shared; mutable workspace is local to a worker. =root_execution= supplies a
generic independent-root execution boundary, while several solvers retain their
own specialized parallel paths.

Witnesses and certificates are not interchangeable. Arena backpointers reconstruct
a solution; replay can establish validity; a separate checker can establish a
named reduction or completeness claim. A returned optimum, a valid witness,
restricted heuristic coverage, and independently checked optimality need different
interpretations. Many source comments correctly state these limits.

Not every “compile” or “evaluate” method is a zero-allocation kernel: cold
construction, serialization, certificate production, layer materialization, and
some convenience wrappers allocate. Preserve these phase boundaries when assessing
performance or proposing abstractions.

** Two rule execution models

| Property | Grounded weighted path | Demand-driven Datalog path |
|----------+------------------------+---------------------------|
| Source schema | =finite-min-plus-rules.v1= | =finite-boolean-datalog-rules.v1= or canonical prepared bytes |
| Carriers | Bounded nonnegative min-plus and Boolean | Boolean only |
| Rule shape | One or two body factors | One to four body atoms; eight variables; arity one to four |
| Preparation | Ground finite scalar equations and product rules | Resolve names/slots, build relations and join plans without grounding all products |
| Evaluation | Sparse synchronous iteration using changed-input frontiers; Boolean lifted into min-plus representation | Round-based semi-naive joins over append-only rows; indexed probes; direct or sparse membership/index structures |
| Storage | Grounded equations and two valuation buffers plus frontier workspace | Plan-owned static indexes; presized row, membership, derivation, and growing-index workspace |
| Evidence | Valuation/replay certificates and support witnesses | Derivation traces or ranked final relations |
| Updates | Retained fact replacement through =RecursiveQuery= | No general incremental update lifecycle exposed by the delivered provider |

Schemas now distinguish the two admission doors even though both wire programs
use the =Program= struct. The prepared Datalog representation bypasses JSON's
one-MiB wire ceiling, but has its own source identity and canonical binary codec.
Equivalent wire and prepared programs intentionally have different identities.

=Demand= plans choose layouts before evaluation. Static direct indexes trade
key-space build cost against estimated probes; sparse static indexes use sorted
keys/buckets. Growing sparse indexes use presized hash/chaining storage. Longer
bodies use a left-deep indexed join on an explicit frame stack. The fixed row
bound and 16-GiB aggregate workspace reservation cap remain policy, not a
universal supported data size.

The two Datalog checkers independently consume the evaluator's certificates, but
share contract admission, tuple storage, unification helpers, and the same
closed-world pass. Trace checking validates named premises; ranked checking
searches for smaller-rank support. Both additionally need completeness, which
is precisely where the shared pass matters.

** Rel frontend and layered execution

#+begin_example
caller-owned source bytes
    → bounded scanner / iterative Pratt parser
    → name and arity admission
    → relational IR construction
    → projection, range restriction, variable binding
    → stratification, body planning, typed dictionary closure
    → positive prepared Datalog layer
    → Demand evaluation → trace + ranked checks
    → checked closure → complement/filter/aggregate materialization
    → next layer → decoded visible relations
#+end_example

The frontend uses byte spans into caller-retained source, flat token/node pools,
and explicit capacity limits. Rich diagnostics and recovering parsing are separate
from the successful execution path. Stage tracking now prevents admission after
an unsuccessful/recovery-only parse and lowering before admission. Exact source
byte identity across stages is still a caller obligation.

The relational IR carries typed literals, relation/column metadata, signed body
literals, strata, auxiliary relations, and provenance for variable-binding domains.
=BodyPolicy::Nary= is the current default; binarization remains available.
The positive projection and the stratified driver are sibling library modules.
This layout is partly dictated by the bare-rustc frontend parity harness, which
compiles frontend sources without the Cargo dependencies of the backend.

Negation is compiled to finite complement facts; comparisons to filter relations;
count/min/max/sum to relations materialized at layer boundaries. Positive closures
are evaluated together until a non-monotone dependency requires another layer.
Per-column domains reduce complements where earlier checked closures justify it;
same-layer dependencies fall back to the full dictionary. Products of domains
can still be large. Integer aggregate results can enlarge the dictionary.

The current =Stratified= result retains readout, final closures, construction
records, and accounting. The driver creates and checks per-layer certificates,
then drops the local plans/certificates. It does not yet return a complete
serializable Rel evidence bundle. =verify_records= reconstructs materializations
from the supplied result using producer construction machinery; it is not an
independent proof that the original source lowered correctly or that the supplied
closures are the ones the dropped certificates established.

The reference evaluator is a valuable independently implemented semantic check
*after parsing/admission*: naive sets and repeated passes, explicit typed values,
and different negation/aggregation mechanisms. It shares scanner, parser, and
admission, so bugs common to those stages are invisible to that differential.
Frontend native/WASM parity likewise checks the compiled frontend representation;
it does not exercise the whole stratified backend.

** Admission, certificates, and authority

Strong APIs use opaque checked objects: binary-composition admission,
verified transition/graph objects, and Datalog =Verified= records. A serialized
receipt is plain data; replay runs the checker again. The new Datalog recording
entries re-admit a wire program or prepared encoding before issuing provenance.
In-process =check_admitted= entries explicitly issue no such record.

Contract and checker identities hash their own enumerated source files, with
tests that bind the inventory. This is source provenance, not compiler/dependency
attestation. It makes identity changes conservative: a comment or unrelated
checker edit changes the package identity, and old records must be rechecked
under the new identity. That behavior is deliberate, but operationally costly
if mistaken for a stable semantic-format identifier.

Not all core “proof” types carry opaque authority. =semantic_theorems= composes
caller-supplied claim statuses and compatibility flags; its ledger checks
bookkeeping consistency. =observational= offers deferred verification returning
the same artifact type as immediate verification. These are different trust
contracts from =ergodis-verify='s opaque checked capabilities.

The documented Lean coverage concerns finite algebraic convergence, Boolean
lifting, and related scalar contracts. It should not be read as a proof of the
Rel parser, stratifier, sparse join implementation, lazy memory backend, provider
ABI, or full relational compiler. No Lean build or proof replay was performed.

* Hosts, persistence, and user interfaces

** Three different orchestration surfaces

1. The optional core =control= module is a native Unix campaign/proposal daemon:
   sockets, files, workers, ticket/session ledgers, rate limits, discovery, and
   steering. It is feature-gated, but remains physically inside the mathematical
   root crate.
2. =ergodis-runtime::Campaign= and =SessionService= are portable synchronous
   state machines over the bounded binary coordinate-restriction pilot. Requests
   carry session/revision/retry identities. Checkpoint restoration replays work;
   cancellation prevents later operations and does not preempt an in-flight
   atomic execute call.
3. Module providers expose coarse prepare/workspace/execute/release operations.
   Some private families support bounded start/advance/admit/cancel operations
   through descriptor selectors. Browser workers schedule those advances and
   publish checkpoints. This is broader executable family coverage than the
   portable campaign's mathematical schema.

These are related, but not one integrated universal campaign lifecycle. Adding
a provider does not automatically supply campaign history, repository activation,
checkpoint restoration, native/WASM UI parity, or cancellation semantics.

** Provider boundary

The ABI has five operations and six status codes, borrowed non-overlapping byte
buffers, opaque =u64= handles, instance nonces, and a fixed header checked before
function fields are accessed. Native plans can use =Arc=; workspaces belong to
instances. Dynamic-library lifetime outlives its instances. Native loading is
explicitly unsafe trusted-code execution, not a sandbox. Digest checking supplies
integrity; callers must prevent replacement during validation/loading.

The JavaScript host separately validates manifests/descriptors, checks WASM
imports and artifact digests, refreshes views after memory growth, and invalidates
instances on traps or output-contract violations. Family payloads remain opaque.
Rust and JavaScript duplicate the manifest/descriptor validation rules; shared
conformance cases are therefore part of the protocol boundary.

The finite-rules provider currently constructs =Prepared= and exposes grounded
evaluation/verification/support selectors. It does not dispatch to =Demand= or
execute private Rel source. Its top-level readout format strings use min-plus
certificate names while a separate semiring map advertises Boolean names: a
generic consumer needs a defined resolution rule before treating those strings

** F11 — P1 resource risk / P2 design: memory bounds mean different things on different hosts

The Datalog evaluator accepts up to 16 GiB of workspace reservation. On native
Unix it uses lazy mmap pages; on WASM and non-Unix it uses =alloc_zeroed=.
Thus the same admitted plan can reserve cheap virtual address space on Linux
and request enormous eager allocations elsewhere. wasm32 cannot address a
16-GiB workspace at all. A null allocation can return a budget error, but host
resource behavior is not a portable resident-memory guarantee.

The checker has its own direct-addressed, eagerly allocated stores. Certificate
and prepared-source decoding allow inputs up to one GiB and allocate additional
owned representations/canonicalization buffers. The stratified driver also holds
closures, materialized complements, evaluator state, and checker results. Tuple
counts and wire-byte bounds are therefore not an end-to-end memory budget.

Recommendation: distinguish logical limits, reserved bytes, committed workspace,
and peak pipeline memory. Supply target/host resource policies before allocating;
account for concurrent evaluator/checker/layer storage. Keep exact refusal and
do not silently change semantics. Windows virtual-memory reservation is an
optional future adapter, not something the portable allocator already supplies.

** What WASM support does establish

The codebase already separates important mathematical kernels from filesystem and
socket effects. x86-specific intrinsics are guarded in the inspected sources;
=bp_osd= has scalar floating-point fallbacks, and linear-code/CSS kernels use
multiversion dispatch with portable bodies. Public binary codecs generally use
explicit little-endian fields. Provider manifests carry target identity and the
ABI checks size/version. These are good starting points for ARM and new OSes.

WASM tests do not execute Unix mmap/drop paths, Windows file replacement/locking,
native dynamic-library loading on Darwin or Windows, ARM instruction selection,
