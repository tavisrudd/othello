** DONE Choose the exact representability rule
For radix =d= and arity =a=, a packed tuple has maximum key =d^a - 1=. Admit when that key is at most =u64::MAX=, equivalently =d^a <= 2^64=. The cardinality =2^64= is not itself a =u64= count, so the existing saturating universe estimate remains =u64::MAX= while the arity-four endpoint =d=65,536= remains valid. The domain is a =u32= cardinality, so its maximum is =4,294,967,295=; it cannot name a domain of all =2^32= distinct values even though the largest value ID =4,294,967,294= fits. Exact ceilings by largest admitted relation arity: arity 1 or 2 =4,294,967,295=; arity 3 =2,642,245=; arity 4 =65,536=. The next arity-three cardinality is =18,446,745,128,696,702,936 > 2^64=.

Keep the core rule in one cold contract helper, applied after relation arity validation at both wire and prepared admission. Decoding prepared bytes must not retain an early blanket ceiling. The private dependency-free lowering mirrors the helper's meaning and checks its constants against the core in tests. The Rel dictionary uses the largest arity of every relation it can hand to the core, including auxiliary and synthetic relations; replay checks the same ceiling against its recorded dictionary. Existing source encodings, schemas, tuple IDs, fingerprints and certificate identities do not change for formerly admitted programs. C1213 has already migrated schema/provenance, so this change requires no additional format migration.

C1213 interaction: for unchanged admitted source bytes, source IDs and certificate bytes remain the same. The contract implementation identity hashes the modified admission source, so a stored C1213 verification record from the previous build will fail =replay= on its =contract= field and must be rechecked to mint a current record. This is C1213's declared build-provenance rule, not a source or certificate format migration.

The exported Datalog =MAX_DOMAIN= constant currently serves two meanings: Datalog key representability and a 65,536-entry weighted resource cap in other crates. Redefine its Datalog meaning to the =u32= field maximum and give weighted its own unchanged 65,536 resource bound; otherwise this task would silently widen an unrelated resource policy. C1206 structured refusal records are still queued, so core currently has only payload-free =Error::Budget=; keep that API compatible and give the private domain refusal its existing =REL0503= found/limit/span shape. The core refusal record is a C1206 follow-up, not a reason to conflate key representability with resource caps.

Red-team cases: arity-three =2,642,246= must refuse before a packed-key collision; arity-four =65,536= must pass despite a saturated universe estimate; a lone unary or binary relation may use a large sparse domain without allocating its entire key space. A wide relation hidden behind a narrow rule still controls the ceiling. Boundary checks distinguish key representability from row, workspace, prepared-byte, frontend-value and layer-tuple limits. No new hot-loop branch or widened key carrier is part of this change.
